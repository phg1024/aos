Record-reconstruction probe: 72 Terminal-Bench trials

For a run that ended on its own, AOS's own records rebuild its state and causality. From the state folder alone (kernel events, trace, call ledger, artifacts and checkpoints), plus aos inspect at v0.1.1, a script answered these correctly in all 72 trials:

  • how the run ended;
  • which budget it ran under;
  • whether the low-time warning was sent.

Every tool error is recorded three times, in agreement, and each one reached the agent. A reader could also recover the final answer of every failed trial that could be checked: 12 of 12, half of them by inference.

For a run that something outside AOS stopped, the records cannot say what stopped it, and they are wrong about its end. In all 5 trials that Harbor killed:

  • the records do not name the stop;
  • they miss 1 or 2 model requests;
  • they end up to 35 s before the kill.

In 2 of the 5, the agent process sent a request after Harbor had ended the agent phase, and nothing in the records shows it.

The records do not say which files a run call changed. Because of this, the frozen script could not find the answer write in 1 of 13 failed trials and in 10 of 41 passed ones.

Scope. No new runs and no GPU. The material is the 72 counted trials of the Terminal-Bench budget rerun (tb2-budget-rerun.html): one single-agent workflow on one model. Multi-agent runs, the bus and leases are not exercised. The plan was frozen as 7d96cfd before anything was scored. Amendment A1, made after scoring, corrects one count and states two definitions; it changes no rule.

Method

  • Records-only answers. reconstruct.py reads each trial's agent/aos-state/ folder and the output of aos inspect --json --tail -1, built from cmd/aos at v0.1.1 (70779be) and run on a copy of the folder.
    • It never opens Harbor's files, the verifier's output, aos.log, relay.log or any result of the budget rerun.
    • The checkpoint holds the message history the model saw. It is an AOS artifact, so it counts as a record. The model itself is never asked anything.
  • Ground truth. truth.py reads only sources outside AOS:
    • Harbor's result.json: the exception, the agent span, the reward, and the aos_exit code that the adapter's shell captured;
    • the verifier's ctrf.json;
    • relay.log, which has every request that reached phg-gpu, by start time;
    • schedule.json;
    • the earlier hand-check of the failed trials.
    Harbor's container artifact folder is empty in every trial.
  • Scoring. score.py compares the two. Each answer is correct, wrong, not answerable (the records do not hold it), or no truth (the records give an answer that nothing outside AOS can check).
  • The hand-answered question. Q10 was answered by reading the records before comparing with the verifier (q10_hand.json).

Gaps, each named by the missing record

1. A run result does not record which files the command changed

  • What is recorded. The command, its exit code, stdout and stderr: in the trace (shortened), in the tool-result artifact, and in the next ledger call. There is no list of files created or changed.
  • Count. The frozen rule matches the answer path and a write operator in the command. It failed in:
    • 1 of 13 failed trials (Q9, seq 27);
    • 10 of 41 passed trials (Q9b): 7 openssl-selfsigned-cert and 3 prove-plus-comm.
  • Example, seq 27 (raman-fitting, strict).
    • Step #19, at 628 s, runs cd /app && python3 - <<'EOF'. Inside the script is json.dump(res, open('/app/results.json','w')).
    • The command has no >, so a script cannot tell it wrote the answer. A reader can, by reading the script, and the hand-check did.
  • The other misses.
    • openssl: cd /app/ssl && … > verification.txt, a relative name after a cd, or openssl genrsa -out server.key after a cd.
    • prove: coqc plus_comm.v, which makes plus_comm.vo without naming it.
  • Effect on Q10.
    • For 6 of the 8 checkable polyglot trials, no record shows the folder at the end. That cmain was still there had to be inferred from the last gcc … -o /app/polyglot/cmain with no later rm. The inference was right in all 6.
    • Seq 63 shows the risk. Its last command ran rm -f /app/polyglot/cmain and then compiled cmain again. Its ls named only main.py.c, so the result looked clean when it was not.

2. A tool refusal is recorded in the trace and as an artifact, not as a kernel event

  • Count. 26 tool errors in 23 trials:
    • 17 run requires command;
    • 7 update_memory evidence rejections;
    • 1 write_file requires content;
    • 1 list_dir on a file.
  • Where each is recorded. Every one appears as a trace tool_error and as a tool_error artifact with the full message. In all 26, the message reached the agent in its next model call. None of the 26 is a kernel event.
  • Kernel events, by contrast. The kernel records only process spawn, transition and exit, a memory header, and backend.retry. There are 8 backend.retry events: 7 malformed actions, and seq 39's connection timeout.
  • Example, seq 25 (raman-fitting, advisory).
    • At 823 s, just after the low-time warning, update_memory was refused. Its message: evidence "#68 (shift-space profile: …" is neither message numbers … nor an artifact.
    • The refusal is trace record #51 and artifact art-000049. The error text is in the next ledger call, so the agent saw it.
    • That call's reply ended the run 7 s later, with an exit reason that reports the fit and the file as done and does not mention the failed note.
    • The kernel log of this run has 7 events, and none is the refusal. An operator who reads only kernel events would not know it happened.

Further finding: the budget is recorded only as text the agent read

  • No process metadata, kernel event or inspect field records whether a time budget was set, its size (879 s) or its kind (strict or advisory).
  • Q8 was answered correctly in all 72 trials, but only by parsing the note text (budget time=879s …, with or without the strict suffix) in the ledger's messages.
  • A run with no budget is told apart from one with a budget only by the absence of notes.
  • The checkpoint's budget_warned records whether the warning was sent, but not the budget itself.
  • Example, seq 41 (cobol-modernization, strict).
    • The warning was in the request that the strict stop cancelled 54 s later.
    • The ledger records that request, with its error. So the records show the warning was sent, and also that no reply to it exists.

What the records do well

  • Endings that AOS made itself are complete.
    • The exit event carries the code, the origin, the reason, and the checkpoint to resume from.
    • The one strict budget exit is labelled time budget exceeded: 879s strict budget of run.
    • The one infra error, seq 39, can be found: its ledger record has the dial tcp … i/o timeout error, and a backend.retry kernel event matches it.
  • Answers that the agent printed can be recovered exactly. In all 4 raman failures, the x0 values in the last printed results.json match the verifier's "Got" values to every printed digit.
  • Records agree with each other. The trace, artifacts, ledger and checkpoints never disagreed on any question that both could answer.

Limits

  • There is one workflow (single agent), one model and one harness. The bus and lease folders are empty in every trial.
  • Q9's ground truth is a careful human reading of the same records. No outside timeline of the container's files exists. Q9 measures a script against that reader.
  • Q4 and Q7 have no truth outside AOS, so they show agreement between records, not correctness.
  • For killed trials, the probe scores the state folder as Harbor left it.
