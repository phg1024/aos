Verification at v0.1.8: Eleven Probes

Where does verification live in AOS, and what can a worker do to the verdict? This page measures it at v0.1.8 (7197ae7), for Chapter 11 (Agents Must Not Grade Themselves). The probe code is new. It ran in an export of the tag, and again at f79bee8 (the two spec-check fixes after it), with the same findings. The workflow probes run the real engine, kernel, artifact store and tools on a scripted backend, which returns actions directly, so no model, prompt or parser is involved. Probes about the checked-in workflows run their specs with the host paths moved into a temporary directory. No model was called.

  • The gate's own records hold. A verifier's own failure stands when the verifier is run again, and only a change to the work clears it. A writer after the verdict makes it stale. No agent with confined tools could publish a verdict, write the state directory, or change the spec the run is gated on (V1, V2, V8).
  • What the verifier measures with, and against, is in the workers' hands. A writer that plants a test script which always exits 0 gets a broken renderer passed (V4). The CUDA evidence the gate requires is produced by code the writer wrote, and a verifier that reads it in full passes numbers the writer chose (V5). In three workflows, the baseline the verifier compares against is written by the writer (V4).
  • The gate requires nothing of a verifier but exit 0. In 9 of the 10 verifying workflows, a verifier that makes no tool call and exits 0 passes the work (V6). The worker side words the verifier's task: the lead's goal reaches the verifier as its user message (V11).
  • The entry agent is outside the freshness check. An entry agent whose write scope covers the work rewrites it after a pass, and the verdict stays pass. The contract accepts such a spec. In the checked-in workflows only write_paths keeps the coordinators out: they can still change their log and final-summary.txt, both of which sit in the workspace the verifier reads (V3).
  • Single-agent --verify is the same model, in one fresh call, with no second attempt. Under best_effort a rejection exits 0. In procedural mode the generated program runs unconfined and wrote outside the output directory (V7).

How to run them

go test -tags verifyprobe -count=1 -v ./bench/verify/

The probes are in bench/verify/verify_test.go and single_test.go, kept out of go test ./... by their build tag. To measure v0.1.8 itself, export the tag (git archive v0.1.8), copy the two files into bench/verify there, and run the command. probe-output.txt is that run. Paths print with temporary directories as <tmp>, a home directory's user name replaced, and no address or hostname.

How the probes run things:

  • The engine as aos run --workflow sets it up. The state directory is protected from the tools, as aos run protects it, and writable mounts exist.
  • The checked-in workflows. Another machine's repository paths and the run scripts' placeholders (__RUN_DIR__, __AOS_ROOT__, __CUDA_HOME__, __WORKDIR__) become directories of a temporary root. allow_gpu is dropped, because this machine has no NVIDIA card and the sandbox refuses a card it does not have. Nothing else in a spec changes.
  • Attempts against capabilities are real write_file calls through the tool runtime, with the agent's mounts and capability set.

Found

Findings

  1. The gate is sound about who ran when. It is blind to what was run. It reads only the kernel's exits and their order. A worker cannot shop for a pass or slip a change past it. A worker can still decide what the verifier measures with (V4), what the evidence says (V5), and what the verifier is asked to do (V11). In three workflows a worker even writes the reference (V4).
  2. Exit 0 is the whole contract with the verifier. Nine of ten workflows rest the verdict on a model's exit code (V6). The one with evidence proves that bytes were read, not that they were checked or where they came from (V5). Everything a prompt asks a verifier to do is advisory.
  3. Freshness is by agent, not by content. "Ran after the verifier" stands in for "changed the work". So the entry agent, left out because its run spans the workflow, can change the work unnoticed when its scope allows it (V3). So can anything outside the kernel's process tree, such as an unconfined command (V11). The checked-in specs are safe only because their coordinators' write_paths name two files. Even those files are in the directory the verifier reads, and final-summary.txt is what a person reads.
  4. Workers are told how they will be judged. Most rasterizer agents carry the verifier's pass rule (V9). The internal/workflow worker gets the contract's verification_steps, but never the reason it was rejected (V7). That is a design choice, either way. The report records it and does not judge it.
  5. Single-agent verification is self-review. The same model reviews in a fresh call, sees less than the worker in procedural mode, and gets no second attempt. best_effort turns a rejection into exit 0 (V7). It is not independent of the worker in any sense but the call.

Proposal, ranked by risk

Proposed only; nothing here is implemented. Ranked by what a failure costs, and how silently it happens.

  1. Bind the verdict to the work's content, not to who ran. When the verifier exits, the engine records a hash of the work: every work-changing agent's write scope, the entry agent's included. At gate time it hashes again, and any difference makes the verdict stale. This closes the entry-agent gap (V3) and changes from outside the process tree (V11). The rule that a verifier's fail stands until the work changes then has a precise meaning: until the hash changes.
  2. Keep the instrument and the reference out of workers' reach. Declare in verification what the verifier trusts: reference paths and tool paths. The contract would refuse any of them that a work-changing agent can write (V4: three baselines). The verifier would run against a frozen copy of the work in its own directory, as pathtracer-bunny-metal's verifier already freezes its baseline, and never execute scripts from the workspace (V4).
  3. Give the gate checks of its own. Let verification declare commands that the engine runs itself, confined, after the verifier, such as a build and a pixel comparison, with a required exit code. Their result joins the verdict. A verifier exit 0 alone would no longer pass a workflow that declares checks (V6). For evidence, record the command that produced it and a hash of the binary it ran, and require that binary to come from the frozen copy, not a worker's directory (V5).
  4. Word the verifier's task in the spec, not in the lead's goal. The engine delivers verification.task to the verifier. The lead's goal follows it, labelled as the lead's, below the spec's (V11).
  5. Refuse unconfined_run in a workflow with a required gate. Today the contract refuses it only on the verifier, but any agent with it can write the state directory the gate reads (V11). terminal-bench has no gate and keeps it.
  6. Make best_effort say what happened. In agentflow and in single-agent mode, a failed or rejected verdict under best_effort exits 0 (V7, V11). Either give it its own exit code, or rename the policy to what it does ("advisory").
  7. Single-agent --verify. Allow a separate verifier profile, and record in the result whether the verifier was the same model (V7). Confine the procedural program as run is confined, and give the verifier the program as well as its output.
  8. Decide, per workflow, whether criteria are disclosed. Record the choice in the spec, so a holdout check can be kept from the workers' prompts (V9). Not a defect today, only an undeclared choice.
  9. Small fixes. Do not copy the verifier's own retryable into the workflow's exit for a failure that stands (V1). Name the runtime's exit origin, rather than leaving it empty (V1). For Terminal-Bench, note in the chapter that the hidden tests run in the agent's container, and prefer a task's separate verifier environment where one exists (V10).

Already in place, and worth keeping in the chapter as the model of an external check:

  • the verdict read from kernel exits, ordered by event sequence;
  • a verifier's own failure standing until the work changes;
  • staleness on a work-changing run;
  • reserved artifact types;
  • the protected state directory;
  • the recorded run_spec;
  • evidence that must be read in the verifier's own process and attached by its delegation;
  • the contract's write-scope rule for verifiers.

After the fixes

The proposal's items 1–6 and 9 are now in place, with two parts of item 7. Item 7's separate verifier model, which needs per-agent models, and item 8, a declaration of which criteria workers are told, stay proposed. A frozen copy of the work for the verifier is not implemented either: the hash below makes any later change visible, and gate checks run against the work the hash bound. probe-output-after-fixes.txt is the run after the fixes. It has two new probes, V4c and V5c, which use fields v0.1.8 does not have, so they live in bench/verify/gate_test.go, which is left out of a run there. With the probe edit made for this run (a spec the contract refuses is now a finding, not a stop), probe-output.txt is reproduced unchanged at v0.1.8.

Replay. The change is versioned in four run.started fields:

  • spec_contract v2;
  • verdict_rules;
  • exit_origin;
  • publish_provenance.

A record without them replays under the old rules. Two runs recorded by v0.1.8's own test harness replay identically under the new aos replay, which notes the older rules it applied. One run publishes a file a run wrote; the other ends at the step limit. The same two runs recorded now carry the new fields and also replay identically. Replay refuses runs with more than one agent process, so no verification gate is ever replayed.
