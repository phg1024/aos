Memory Phase 3 Evaluation: Live Run

An independent analysis by the evaluation session of the phase-3 live run reports/pathtracer-bunny-phase3 (binary 74510b7), compared with the memfix run reports/pathtracer-bunny-memfix (binary eceb917). The E3 count is this session's own reading. It does not use aos code's tallies (aos code made none for this run).

Result, mechanics: compaction works as designed.

  • 21 compactions, 0 oversized. The smallest segment is 17 messages / 86,917 characters (memfix: 2 messages / 1,236).
  • Live history goes over the threshold H = 157,284 characters only during the one-step handoff before a compaction, by at most 18,709 characters. After every compaction it is at or below L.
  • Agents wrote working memory: update_memory 57 times in 13 processes, 40 of the 42 final entries with evidence.

Result, behaviour: agents almost never looked anything up. In the whole run there was 1 search_memory call and 0 read_memory calls (memfix: 0 and 9). E3, counted separately:

  • Superseded or wrong fact cited as current: 8 instances, plus 4 possible.
  • Experiment repeated: 3, plus 3 possible. B3 was added after this report first said 2 (see the B3 note).
  • Invented rationale recorded: 7, plus 4 possible.
memfix was counted at 2 and 2, but by a narrower reading. These numbers are not the same measurement (see Against memfix). What can be said: the failure phase 3 was built for still happens. In 5 cases (A6–A8 and B2 in the round-7 writer, B3 in the round-5 writer) the right answer had been archived by compaction and the agent never searched for it. All counts here are lower bounds: the full read missed B3. In 2 more (A3, A4, the round-3 writer) the agent overwrote its own working-memory entry and lost what the archive still held.

Outcome: 8 rounds, stop rule met, every verification passed (one verifier was killed by a backend outage and re-run). Final 30.813 ms, 3.5588x over this run's own round-1 baseline. Three environment-fault windows are excluded from E3: an Xcode license prompt and two model-backend outages. The outages cost 4 h 15 m. Failed backend calls count as steps: one verifier ran out of steps that way.

  • Peak live and oversized: no compaction was oversized (0 of 21 memory.compacted events). Live history crossed H = 65,536 × 0.8 × 3 = 157,284 characters 22 times. Each time it stayed over H for at most two checkpoints: the step that crossed H and the handoff step after it. Compaction followed every time, except pid-000009's last crossing, where the process exited 34 characters over. The largest overshoot, 18,709 characters (pid-000012 art-001332 to art-001335), comes from one large tool result that jumped over H in one step. The design rule "peak ≤ H unless oversized" holds except for that one-step handoff delay, which the design itself adds. After compaction, live history was at most 78,607 characters, under L = 78,642. The smallest gap between compactions in one process is a 17-message segment, so there was no thrash.
  • Ignored handoffs (4 of 21): pid-000003 (art-000132), pid-000009 (art-000813), pid-000015 (art-001608), pid-000025 (art-003062). Each was the writer's first compaction, and the writer had no working memory yet. Its first update_memory came after the compaction, so until the next compaction the header carried no working memory. pid-000003 never compacted again, so its header never showed one.
  • Evidence syntax: 12 of the 69 update_memory attempts failed. 11 failed on evidence syntax and 1 on a bad section name (pid-000007). The rejected evidence strings were #12, #43, #45, #75 #76 #86, task goal #1 (twice), goal #1, history #17 (6 trials), [#21] build OK, [#5] writer log … and pathtracer_benchmark.json read in msg #7. Every process retried with a plain range and succeeded. 11 of the 13 processes that wrote working memory hit this at least once. A single #N is the form the history itself uses. Accepting it is a small runtime fix for aos code.
  • Stale entries: no process ever deleted an entry (0 delete calls), and an entry written under a new key never replaces the old one.
    • The coordinator's final WM v4 (art-003287) still has next/round6-verify-pending ("Verifier run FAILED … NEXT ACTION: re-delegate verifier") and next/round7-plan. This is after its #328 note "Replace the stale round6-verify-pending entry" and its #352 note "so no stale 'next' entry remains".
    • pid-000018's next/round6-plan was never updated after the plan changed at #18.
    Neither stale entry led to a wrong action. It is a working-memory hygiene finding, not an E3 instance.
  • Entries rewritten in place lose content. An update to an existing key replaces the whole entry. Two E3 instances below come from this:
    • pid-000009 overwrote round3-state at #306, after the compaction notice at #305, with a version holding only the latest results (A3, A4).
    • pid-000022's v3 to v4 rewrite of decisions/r7-findings kept "REJECTED leaf2 (#64)" but dropped "(tie-break order changes)" (A6).
  • "adopted=false" in update_memory results (aos book's question). It is the normal case. adopted is true only when adoptMemoryVersion finds a version this process already wrote for the same update to the same parent, which is what a step replayed after a crash produces (internal/runtime/workingmemory.go:285). False means a new version artifact was written. The same field on memory.compacted means the same for segments (priorSegment, runtime.go:1440). All 21 compactions and all 57 updates were fresh.
  • Did working memory reach the next turn? By design, between compactions the update_memory call and its result sit in live history. The header snapshot is refreshed only at compaction (runtime.go:1458, MemorySnapshot = WorkingMemory). In the checkpoint right after each compaction, memory_snapshot equals the last version written before it in 17 of 21 compactions. The other 4 are the ignored handoffs above, where no version existed yet. The header text itself is not logged (calls.jsonl keeps message deltas and a request hash), so this rests on the checkpoint fields and the code, not on observed prompt bytes.

  • There is no delay, no backoff and no limit on consecutive backend errors.
  • Each failed call counts as a step.
  • A dead backend costs a full 3,600 s per timeout. The workflow has no wall-clock budget.
  • An outage reaches the agent as an instruction to change strategy for a fault that is not in its code.

Caveats
