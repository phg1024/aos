IPC Live: The Metal Variant and Its Preflight

workflows/rasterizer-bunny-metal-ipc.json is the Metal rasterizer workflow with mail and artifact handles, so that a live run can test Chapter 8's contract with a real model. It has only been run with a scripted model, and it is not scheduled to run live.

  • Metal works inside the confined run on this Mac. The spec's exact clang++ ... -framework Metal command built a small compute kernel, which ran on the GPU and returned correct results, for the writer, the benchmarker and the verifier, whose workspace stayed read-only.
  • Through the real aos run: a too-large refusal, a publish, a handle, a denied read, a verifier's wait, a mail, a resume, a read to the end, and a required verdict.
  • The preflight shows the machinery works. It says nothing about what a model does. Its program is not a rasterizer, and its verdict is scripted.

1. The Mechanism

The spec holds two placeholders, __RUN_DIR__ and __AOS_ROOT__, as terminal-bench.json holds __WORKDIR__. reports/ipc-live/render.py <name> fills them into reports/ipc-live/runs/<name>/workflow.json. The spec format needed no change, and run.sh does this for a run, so no hand edit is needed.

  • Isolation: render.py refuses a run directory that exists. Workspace and verification are runs/<name>/metal-workspace and runs/<name>/metal-verification, and runs/ is git-ignored.
  • What a run needs from reports/rasterizer-bunny, read-only, and not in git, so this run is not reproducible from a clean checkout: baseline/ with its binary, sources and headers, baseline_benchmark.json, optimized_benchmark.json, final-summary.txt, scene-closeup.json, scene-side.json, scene-small.json, and assets/stanford-bunny.obj. render.py checks they exist and copies nothing.
  • Grants: message_agent for all four; publish_artifact for the coordinator and benchmarker; list_artifacts for the coordinator and verifier. read_artifact is always available. No path, network, skill or other tool is added: TestTheIPCMetalWorkflowWidensNothing compares it with the Metal workflow field by field.

That is about 190 to 300 calls for three rounds. No wall time is claimed: at L seconds a call, 300 calls is 300 L, so 60 minutes needs about 12 seconds a call, including commands.

3. Environment

  • AOS_LLM_BASE_URL, AOS_LLM_MODEL, and the key, as usual. No address is in the spec or here.
  • AOS_LLM_CONTEXT_WINDOW must be set, and run.sh refuses to start without it: otherwise the default policy applies, with no handoff and 2,000-byte mail batches. Use the model's real window. It has to be at least about 60,000, the floor below which Validate refuses at the default ratio of 0.8. A window of 128,000 to 200,000 is a sensible cap on a model with more: a very large one leaves compaction, and so archived mail, rarely exercised.
  • AOS_LLM_MAX_TOKENS at least about 12,000: publish_artifact has no path form, so a model retypes the raw record, 20 to 29 KB, as output.

4. What the Prompts Do That Could Bias the Result

  • The record is kept out of the workspace. In ordinary practice it would sit on disk, where the verifier could read it. The prompts keep it in $TMPDIR, and tell the verifier it is not on disk, so that the handle is needed at all.
  • Its size is designed. 20 trials with the whole of /usr/bin/time -l: 20,285 bytes in the preflight, and 28,691 with the sandbox noise below. A model that records less may never pass 16 KiB, and nothing refuses.
  • "Get the whole record to the coordinator" invites an inline send, which is what makes a refusal likely. The system prompt's tool line already says what artifacts is and that an ID in a body grants nothing, so a model may publish first, and too_large would then be not exercised.
  • The verifier's reading is required: a record it could not read is a FAIL. So its read shows it can, not that it would choose to.
  • The route is hinted. The coordinator is told a verifier may pause, that it can mail a paused process, and that delegating resumes it; and to put its own process_id in each goal, because nothing else tells a child its delegator's. No step-by-step sequence is given, and no refusal text is quoted.
  • A retyped record is not the record. The verifier checks the JSON against the model's copy, and a transcription error or an invention would be checked against itself.

5. What Would Mislead in a Comparison With the Old Metal Run

  • It had no mail, handles or raw-record duty, ran at least 8 rounds with 10 allowed, and may have used another model and an older AOS with larger step limits. Its timings came from many more tries.
  • This variant adds work every round: 20 trials rather than 5, and a verifier reading a record. Fewer rounds means a slower best time for reasons unrelated to mail.
  • So a difference in speed says nothing about IPC, and neither does one in calls or tokens. Compare the contract's situations, not the rasterizer.

6. What the Preflight Found

  • Each Metal start under the sandbox prints three sandbox_extension_issue_file failed lines on stderr, about the shader cache, and the kernel still runs. They add about 8 KB to a record that captures stderr, and a model may take them for a failure. Shaders compile at startup anyway, outside the timed region.
  • A child learns its delegator's PID only from its goal, as nothing else tells it: decision 9's parent keyword is not built. And a delegator reads mail between delegations only, so a question needing an answer means a wait.
  • $TMPDIR is per process, so a recovered benchmarker loses its record.
  • message_agent leaves no mailbox_message send record, as a send does; analyze.py reads its tool result instead.
  • Found by analyze.py, not by this workflow: under the default policy, while mail keeps coming, a tool's result is archived before any call has it. See section 7.

7. A Limit in the Batches, With a Reproduction

Under the default policy, for an unknown window, a batch takes KeepMessages - 1 messages and its note takes the last place, so nothing older stays live. A tool call's result, from the step before, is archived before any model call has it, for as long as full batches keep coming. All a model can do is read it again, and again. reports/ipc-step-4-e2e/run.sh shows this: its receiver calls read_artifact while 256 messages are waiting, and the next requests hold mail and no page.

It does not arise with AOS_LLM_CONTEXT_WINDOW set, which has no count limit and leaves room. Before batches the same result was archived too, once. Not changed here: it is reported to the review.

8. Commands

# The preflight: a fake model, no network beyond this machine, about a minute.
go build -buildvcs=false -o /tmp/aos ./cmd/aos
reports/ipc-live/preflight/run.sh /tmp/aos pf1

# A state directory with nothing in it, to see "not exercised":
mkdir /tmp/empty; python3 -I reports/ipc-live/analyze.py /tmp/empty

# A live run, if one is ever scheduled. The endpoint and window come from the environment:
AOS_LLM_CONTEXT_WINDOW=<the model's window> AOS_LLM_MAX_TOKENS=12000 reports/ipc-live/run.sh /tmp/aos live1 --time-budget 60m
python3 -I reports/ipc-live/analyze.py reports/ipc-live/runs/live1/state

9. Not Done

  • No live run, and nothing against a real model.
  • The preflight's program is not a rasterizer, so no image comparison ran on Metal output. Its verifier did run the CPU baseline under the sandbox, and read the image's header.
  • The analyzer's classifications have only met scripted runs, and a model's actions may fall under "none of these".
