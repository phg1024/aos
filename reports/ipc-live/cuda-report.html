allow_gpu and the CUDA Variant

allow_gpu lets a confined run on Linux reach named NVIDIA cards. workflows/rasterizer-bunny-cuda-ipc.json is the mail and handle design on CUDA. No real kernel has run through it, and no real model has been near it.

  • Through aos's own helper on the target machine: with the grant, cuInit returns 0 and nvidia-smi -L lists the card; without it, 304 and exit 255.
  • A dry run through the real aos run there: nvcc inside the sandbox from a read-only toolchain, a too-large refusal, a handle, a verifier's wait, a read to the end, a verdict. It allocated no GPU memory.
  • Before a live run: a confined command can reach the user's service manager, and an API key in the environment reaches every model-written command. See section 4. Fixed since, in ab0950b: see reports/sandbox-socket-key-signal-fix.html.

1. allow_gpu

The form: "allow_gpu": ["GPU-<uuid>"], in a capability set. Empty, the default, means no GPU, and there is no way to say every card. A child gets the cards it asks for that its parent can grant; Recover keeps them. The UUID is resolved at each run from the driver's own description of its cards. One not on the machine refuses the run, as an unconfinable command is refused.

Landlock grants by path, and a new thread's path is not known in advance. The user decided this. Against a test process of the same user, measured: writing oom_score_adj and coredump_filter became allowed; comm, clear_refs, and reading environ and mem stayed refused

Left out: nvidia-uvm-tools (profilers), nvidia-modeset (display), nvidia-caps (MIG). cuInit and nvidia-smi work without them; a real kernel has not been run yet.

2. What It Does Not Do

  • The rule stops at the device. Landlock cannot isolate what a process does on the GPU, or between two users of a card. No budget meters GPU use.
  • Per card is enforced only for the card's own node. On a machine with two cards, another card's /dev/nvidiaN stays closed, but nvidiactl and nvidia-uvm are shared, and Landlock grants a file, not an ioctl on it. A process can at least see that the other card exists. What more it can do through them has not been measured: this machine has one card, and the two-card machine is off limits for now. So do not treat this as protecting a second card's workload until it is. CUDA_VISIBLE_DEVICES is a convenience that the sandbox sets, and a process can change it.
  • macOS: no confinement of the GPU exists, and every confined command reaches Metal with or without this. An allow_gpu entry there refuses the run, since it names an NVIDIA card that is not there, and its presence never implies Metal is held back. The profile does not change: TestDevicesChangeNothingOnMacOS.
  • Off by default: a set without it marshals as before, and a policy without devices adds no rule. No marker is needed, as no old record can hold it.

3. The Workflow

  • Same design as the Metal variant, with its biases: see report.html, section 4. allow_gpu on writer, benchmarker and verifier, which run GPU code. The coordinator only delegates it. A read-only __CUDA_HOME__, since a toolchain under home is not on the sandbox's read list.
  • No machine in it. __RUN_DIR__, __AOS_ROOT__, __CUDA_HOME__ and __GPU_UUID__ are filled in at the start. TestTheIPCCudaWorkflowGrantsOnlyWhatItNeeds checks for addresses and home directories.
  • Differences that matter: the CPU reference's binary and timings come from another machine, so the verifier rebuilds the baseline, and the benchmarker times a baseline here. Its old numbers are recorded, not compared.
  • No network, anywhere. No agent or delegable holds allow_network, and the web tools are gone from the grants and the prompts, so nothing can be granted down: a child's set is cut to what its parent can grant. The test checks this. With network, a model-written command could reach the LAN, where the cluster's Jobs API has no authentication, and leave the sandbox that way. The Metal variant inherited the writer's and coordinator's network from the original workflow. It is left alone, since it is not scheduled and its prompts lean on the web, so that is not a one-line change.
  • Bias from that: the old runs had web access, and this one does not, so a model here works from what it knows and from the sources on disk.
  • Sized for the window. A first version and one optimization round, with the verifier running in the first round whatever the benchmark shows, and checking the raw record before it renders. Step limits: coordinator 30, writer 35, benchmarker 15, verifier 20, per process. Two rounds: 30 + 2 x (35 + 15 + 20) = 170 calls. One repeated verifier and benchmarker makes 205. It is not a hard total: the job limit is. The assumption is about 25 seconds a call, from the book session's reading of this model family's earlier ledgers: means of 16.4, 19.8 and 29.1 s, median about 10 s, so 170 calls is about 71 minutes and 5,400 s holds about 216. A process that hits its limit is data.
  • The raw record gains the card's memory and utilization before and after each trial, since others may use the card, and uses /usr/bin/time -v. It was 23,869 bytes in the dry run, without a real program's output.

4. Before a Live Run

  • Out of the sandbox through the user's service manager. With network off, TCP is refused, to the cluster's Jobs API and to loopback alike. But Landlock does not cover connecting to a Unix socket by its path. Measured with the sandbox's rules on the target machine: /run/user/<uid>/bus and systemd/private connect, and systemctl --user answers, and reports the state of the Ray service. So systemd-run --user should start a command outside the sandbox. That was not tried, since it would really start one. Removing network does not close this, and no spec can. UDP also stays open, as sandbox_linux.go says.
  • The API key. aos reads it only from its environment, and run inherits that environment, so a model-written env prints it. Measured: the command saw the variable. A mode 600 file does not change this, since the job has to export it for aos. The preflight needs no key. Not fixed here.
  • Signals. A confined command on Linux can signal any process of the same user: kill -0 against a process outside the sandbox was allowed. Landlock's signal scoping exists from ABI 6, and AOS does not use it. The job runs as a user who also runs other services. Not fixed here.
  • The placement is outside what the worker advertises. That worker advertises no GPU to Ray. This job uses its card regardless, by the user's decision, for this test only, with the other service unloaded by its owner during the window.

5. Running It

Scripts in reports/ipc-live/cuda/: sync.sh puts what a run needs on the machine, submit.sh submits and refuses without entrypoint resources, and job.sh is the one job. Everything about the cluster comes from the environment. job.sh finds the card's UUID at start and refuses unless exactly one matches. A kernel check runs first and fails fast, and the job ends under a time limit.

  • Bounds: the step limits in section 3, a 60-minute advisory budget, and a job limit of 5,400 seconds by default, plus 60 before a hard kill. The preflight's own limit should be 300 seconds: the dry run took 7 seconds, and the 20 kernel runs and the check add to it, unmeasured.
  • What survives a killed job: the state directory is written as it goes, on local disk, and analyze.py reads it. job.ended is written on any exit the script can catch: its absence, with the job not running, means a hard kill. Ray's status says the rest. Nothing resumes it.
  • When it ends: the script kills anything of its own on the card and prints what is left there.

7. Not Done

  • A real CUDA kernel: it waits for the window. So nvidia-uvm-tools and the others being unneeded holds for cuInit and nvidia-smi only.
  • A second card, through the shared nodes.
  • The service manager, key and signal findings in section 4.
  • A full run through Ray: only one trivial job has been submitted, and it failed on my own quoting, after landing on the right node.
  • Any run with a real model.

8. The pf1 Preflight and the Kernel Check

The first preflight stopped at the kernel check, outside the sandbox and before aos started: kernel_ok=0, exit 6, about 1.5 seconds. The cause is not established. The check did not look for an error after the launch, so a launch that failed would look exactly like this. The dry job skips running the check, so this was its first time on the card.

What was measured, compile only

Device code embeddedArchitecture macro
nvcc -O2 -std=c++17Binary for sm_75, PTX for sm_75750
nvcc -O2 -std=c++17 -arch=sm_86Binary for sm_86, PTX for sm_86860

The card reports compute capability 8.6. nvcc is release 13.3 and writes PTX 9.3. The driver reports CUDA 13.2. Output.

So the default build does carry PTX, according to nvcc --dryrun, and the earlier lead that it had none does not hold as stated. On a 3080 it would have to be compiled by the driver when it loads. One candidate cause is that a 13.2 driver does not accept PTX 9.3. That is an inference, and nothing here has tested it.

What the check does now

  • Names the failure: it checks cudaGetLastError after the launch and cudaDeviceSynchronize after that, and prints the error's name. A wrong result prints the first wrong value, how many were wrong, and how many still hold a marker written before the launch, which separates a kernel that never ran from a wrong answer. It also prints the launch time.
  • Answers for both builds: it compiles and runs the default and -arch=sm_<card>, taking the architecture from the card through nvidia-smi. Both always run. kernel-check/results.txt records both, with the toolkit, driver and PTX versions.
  • Decides on what agents use: job.sh reads the flags from the rendered workflow, and only that build's result can stop the job. Flags that are neither form stop it too.
  • job.ended: the check used to exit before the trap was set, which was not deliberate and contradicted section 5. The trap is now set first, so every path after the argument checks writes it.

Proposed, not made

Two lines in the workflow, which are the user's and Book Writer's call:

  • Change "Build with exactly" to nvcc -O2 -std=c++17 -arch=sm_86 ... in the workflow and in fake_model.py. Agents would see the flag in their task, with no hidden environment variable. job.sh then decides on that build without further change.
  • Add to the task: "After every kernel launch, check cudaGetLastError and treat an error as a failure to report."

The reason to decide before the window: with the task unchanged, a failing default stops the job, so the window answers the compile question but tests nothing under the sandbox. With the flag, the job goes on if the sm_86 build passes, and the default's result is still recorded. Pinning would also avoid compiling at load time for agents' binaries. The sandbox gives no write access to ~/.nv, so that compile might repeat at each start, which would land in the workload's numbers. That is unmeasured.
