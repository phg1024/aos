The Six Live IPC Runs, live1 to live6

After v0.1.5 the IPC contract ran six times with a real model. The task was to write a CUDA rasterizer for the Stanford bunny, time it against a CPU baseline, and verify it. A coordinator delegates, in rounds, to a writer, a benchmarker and a verifier. Their commands run confined on a Linux machine with one RTX 3080, and only that card is granted. live1 to live4 each changed AOS. live5 was interrupted, and live6 ran clean. This page stands on its own: the run records are gitignored and are not in the repository.

  • live6: verdict pass, art-000418 by verifier pid-000008. analyze.py calls it CLEAN. Each of the four delegations with handles put them inside delegate, and all eight handles were granted.
  • live2 and live3: the kernel recorded a pass from a verifier that never read the benchmarker's record. Only analyze.py caught it.
  • Not yet shown by any real run: an exit refused for unread evidence, an unverified verdict, a second model or task, or a real injection attempt. See section 9.

2. live1: it never reached the model

  • Records. The coordinator's model call failed 12 times in a row, because the job could not resolve the model server's name. Then the coordinator exited 1. No request reached the model, and no verifier ran.
  • What changed. The job now names the model server by address. That is the submitter's environment, so there is no commit for it. 60da2bb makes submit.sh pass the model client's timeout, 1200 s unless set. live1 had run with the client's 2-minute default, and a full 12,000-token reply would outlast that.

3. live2: a pass from a verifier that read nothing

  • Records. The judged verifier, pid-000010, read no artifact and exited 0. The kernel recorded a pass. The benchmarker's record, art-000319, was 3,580 bytes the model had typed. All three verifiers (pid-000006, -000007 and -000010) read no artifact. analyze.py exits 3: UNCLEAN PASS, for both reasons.
  • Durations. 51 run calls could be parsed. 39 of them asked for a timeout, and every one was a bare number such as "300". The other 12 asked for none. A bare number fell back to the 60-second default, so every command ran with it.
  • What changed.
    • e75b622: publish_artifact takes a file's bytes from a path, up to 1 MiB, with its sha256.
    • 7188082: the handle-only workflow, where the benchmarker works in a directory only it can reach.
    • 09db0be: a bare number in a duration is read as seconds, and a value the tool cannot read is a tool error.
    • 202ea95 and 32d22fe: a test and the report.

The 09db0be commit message says "All 51 timeouts". 51 is the count of run calls, and 39 of them asked for a timeout. The commit is left as it is, and this page has the right count.

4. live3: the record reached one verifier, and the judged one read none

  • Records. The benchmarker published its record, art-000172, as 258,263 bytes from a file.
  • Verifier pid-000006 had its read refused and exited 1. It said it could not reach the record.
  • Verifier pid-000007 had its read refused too. It parked in a wait, and the coordinator mailed it the record as a handle. It read all four pages and exited 0.
  • Verifier pid-000009 was a new process and the one judged. Its read was refused, it read none of the record, and it exited 0. Its report names art-000172. The kernel recorded a pass, and analyze.py exits 3: UNCLEAN PASS.
  • What changed.
    • 6252c8a: handles at a delegation, and a pass bound to the evidence the workflow declares.
    • 0275b77: the report, and a fix to test_path's clean path.
    • 8718ad8: live3 recorded a 3600 s budget under a 5400 s job limit, so the job's limit is now the run's time budget.

5. live4: clean, but two attachments were dropped without a word

  • Records. analyze.py calls the pass CLEAN. The judged verifier, pid-000009, read the declared record art-000465 to its end, two pages.
  • The dropped attachments. Twice, at model calls 186 and 504, the coordinator wrote artifacts at the action level, beside delegate rather than inside it. The parser read only the inside, so nothing was attached or refused, and the coordinator was told nothing. pid-000009 got art-000465 only by mail, after a refused read and a wait.
  • The earlier verifier. pid-000005 had its read of art-000167 refused. It failed the round on a closeup mismatch of 0.6388%.
  • The verifier's words against its files. pid-000009 called the four scenes "pixel-identical", 0.0000% diff. Its own renders differ from the CPU renders in 93, 4, 40 and 9 pixels, each by 1. That is within the 2-level tolerance, but it is not identical. Reading bytes is not understanding them.
  • What changed. 8d5ff6e: a delegation's artifacts are read inside delegate or at the action level. Two places that disagree are refused. The delegator's result line says attached= with the ids, or none.

6. live5: interrupted, no verdict

  • Records. At 23:36:05 PST the job received SIGTERM, and every process exited. The one model call in flight was cut off by the signal. The records do not say why the job was signalled.
  • The refused delegation. At model call 98 the coordinator attached art-000089 to a benchmarker delegation, inside delegate. art-000089 is a runtime record, so the delegation was refused and nothing started. The next delegation went without it.
  • The granted delegation. At model call 204 the coordinator attached the benchmarker's record, art-000179, to the verifier. Verifier pid-000006 read it to its end, three pages, and passed. Then the coordinator started writer pid-000007 for another round, so the kernel marks the verdict stale, and the run ended before a new verifier ran.
  • Other refusals. The coordinator also had two read_artifact calls on runtime records refused, and one call to a tool named raw_record, which it does not hold.
  • What changed. Nothing.

9. Not yet shown

  • No real model has had an exit refused for unread evidence. In every run, "exits refused for evidence" is 0.
  • No verdict has been withheld as unverified. That path, and the refused exit, are tested with scripted replies only.
  • One model, one task, each run once. Nothing here says how a second model or task would go.
  • No real injection attempt. analyze.py found no body or tool output imitating a runtime line in live6.

10. Running again

The model server's API key was removed from the run machine on 2026-11-08. That was reported to this session, not checked here. job.sh in live mode stops before aos starts unless the key file exists with mode 600. So a live rerun needs the user to approve placing the key again. Preflight runs use the scripted model and need no key.
