Handles at a Delegation, and a Pass Bound to Its Evidence

In live3 all three verifiers had their first read of the benchmarker's record denied, because a new process could not receive a handle. The verifier that was judged read none of the record and exited 0, and the kernel recorded a pass. Only analyze.py caught it, afterwards. This phase closes both gaps.

  • Scripted runs on the target machine, outside Ray, with no CUDA context: the clean path passes with no read refused and no wait. live3's pid-000009 path, refused read then exit 0, comes out unverified, and the job exits 1.
  • The kernel and analyze.py agree on the same records in all 17 end-to-end scenarios, and a second judgement from those records matches the first byte for byte.
  • Not run: any real model, and this binary and workflow on the card. Replay refuses these runs: see section 5.

1. Fix 1: a handle at a delegation

A delegate action and spawn_agent take artifacts, a comma-separated list as on message_agent. A model may also write a list on a delegate action.

  • No second rule. The check is mail's checkHandles, on the whole list, before the delegation starts. One handle the delegator cannot read refuses the delegation as a tool error it reads and goes on from. Nothing starts and nothing is granted. The refusal is logged as capability.denied.
  • The record. A delegation_handles artifact, produced by the process delegated to, before its first step. readRightsOf reads it as it reads a received message, so the right belongs to that chain. A new process of the same agent gets nothing from it.
  • Why a record and not process metadata. Delegating to a parked process must attach too, and a process's metadata does not change after its spawn. One record covers both.
  • The model is told. The first message names what came attached, and the prompt beside delegate says a new process needs it attached again. That was pid-000009's misreading.

2. Fix 2: a pass bound to declared evidence

"verification": {"policy": "required", "verifier": "verifier",
  "evidence": [{"publisher": "benchmarker", "type": "raw_record", "from_file": true}]}

It resolves when checked to the latest artifact of that exact type from that agent under the run's root, and the verifier's own chain must have read it from the start to its last page. The check reads the kernel's process table and the runtime's records of tool results, which no model writes. It lives in the engine, which needs no inference provider.

3. The workflow and analyze.py

  • New file: workflows/rasterizer-bunny-cuda-evidence-ipc.json. The workflow live3 ran stays byte for byte (sha256 d0ab28df…), now pinned by a test, as live2's already was. A test also holds capabilities, delegable authority, mounts and allowed agents equal between the two: no process reaches anything new.
  • Changed in it: the declaration; the coordinator attaches at delegation, with the wait route still available; the benchmarker publishes as raw_record; the verifier no longer exits 1 for a record it could not read; and the step budgets below.
  • job.sh now renders the new workflow, so re-running the old one means an older commit.
  • The 26 situations count as before. live2 stays 3 of 26 and live3 7 of 26, both pinned by tests. A separate block has a new denominator of 4: a handle attached at a delegation, an attachment refused at a delegation, an exit 0 refused for unread evidence, a verdict withheld as unverified. A refused attachment also counts in the existing "a read denied", as a refused mail attachment always has.
  • New lines: attached at delegation by …, declared <type> by <publisher>: <artifact>: <status>, exits refused for evidence: N, UNVERIFIED: …, and DISAGREE: …, which exits 3, if a verdict and the records ever part.

4. The question-by-mail line

Not changed. The limit to writer and benchmarker senders came with the Metal preflight, whose scripted writer asks a question by mail. A verifier's route was a wait, counted on its own line. Nothing in the contract separates them, so I find no reason to keep the limit. But widening it alone would not count msg-000001: that body holds no question mark, so the "?" test misses it too. Moving either changes a count the book may quote, so it is left for a decision.

6. What pf4 no longer covers

pf4 ran an older binary and the old workflow on the card. It did not run this binary, the new workflow, a handle at a delegation, the exit check or the verdict's new branch. Off-window runs cover those with a stub compiler, not with the real compiler and kernel. job.sh's compile check is the one real-compiler step that ran (test_steps.sh), and it stops before running. The sandbox code is unchanged and so are the grants, so the card path should hold, but that is reasoning, not a measurement. pf4's duration-fix gap from the last phase also still stands.

8. Open

  • Whether a real model attaches the handle and publishes under the declared type. Only a live run can show it.
  • The evidence is bound to bytes read, not understood. A model can read a record and misreport it.
  • A verifier can still exit 1 over an unreadable record, against its prompt. That fail stands until the work changes.
  • aos-tui's progress line still shows a verifier's nonzero exit as FAIL during a run. The verdict is the record.
  • The question-by-mail line, in section 4.
  • web_search, web_fetch and ttl still have no upper limit, from the last phase.
