macOS Sandbox and launchd

The Linux work suggested that launchctl submit might be the macOS equivalent of the systemd-run escape. It is not: launchd refused it from inside the sandbox, while the same submit ran from outside. Two narrower things were open. One is closed for the launchctl tool, and neither is closed for a program that speaks launchd's protocol itself.

  • No escape found: creating, starting, stopping, signalling or removing a job was refused.
  • Closed: a confined command can no longer run or copy /bin/launchctl.
  • Still open: a program calling launchd directly disabled a service from inside the sandbox.

1. What launchd allowed

macOS 27.0.1. Measured under the profile as it was at dbea4ee, with no network, against one job of my own holding a canary variable. Nothing else of the user's was touched. Results.

From inside the sandboxResult
submit, bootstrap, loadRefused. No marker written. From outside, the same submit ran.
kill, kickstart, stop, bootout, remove, setenvRefused. The job's pid did not change.
print gui/<uid>/<label>Answered, including the canary. An API key in a user agent's environment would be readable this way.
disable, enableSucceeded. launchd stores this across reboots, so a command could turn off this user's login agents, or turn on one already disabled.

2. The fix

The profile now ends with one rule, in internal/sandbox/sandbox_darwin.go, placed after the grants so that a policy naming /bin does not reopen it:

(deny process-exec file-read-data (literal "/bin/launchctl"))

Denying the read stops a copy being made. A copy made outside and run outside was killed with exit 137, so that route looks closed anyway; the cause was not investigated.

3. What it does not stop

A small C program built outside and run confined, with the rule in place (direct.c):

Direct callResult
Disable my own labelSucceeded: the label showed disabled afterwards.
List servicesRefused, error 1. The same program listed 595 services from outside.
Print a service (directprint.c)Not established. One attempt, returned error 22, which may just mean my request was malformed.

The program was built outside. Whether a confined command can build or script one was not tried. cc failed in the bare test profile with or without the rule, cause not investigated. Python and its ctypes are readable there.

4. The option not taken

Removing the task's bootstrap port before sandbox-exec (nobootstrap.c) stops the direct call too: it returned 32 and the label stayed enabled. It was not taken because of what it breaks, and because Go's standard library cannot make that call, so it would need cgo or a small C helper.

A device grant changes nothing in the macOS profile today, so limiting this to runs without Metal would be a new distinction. That is a decision for the user.

5. Tests

  • TestLaunchctlIsOutOfReach runs the real profile: print and submit refused, copy refused, no marker, for the plain policy, one that grants /bin, and one with network.
  • 4 of 4 mutations fail it (mutation.txt): rule removed, execute only, read only, wrong path.
  • internal/sandbox, internal/tools, internal/capability and cmd/aos pass on the Mac. go test ./... was not run, since it rewrites the probe results.

6. Left as it was

  • Left behind by this test: launchd's disabled list now holds aos.sandbox.own.59684 => enabled. No job has that label. Removing the entry was not attempted.
  • Still open on macOS, not in this fix: allow_network also opens Unix sockets, and an inherited socket survives into the command. See the earlier report, section 6.
  • Not probed: launchctl bootout gui/<uid> and reboot, which could end the login session. They are behind the same rule, but a direct call was not tried.
