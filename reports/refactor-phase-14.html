Phase 14 Report: A Run That Survives Its Own Death

Design-review item 6. A run now writes a durable record while it runs: an engine trace joined to kernel event IDs, and a ledger of every model call with usage and a hash-checked prompt. A run that is SIGKILLed mid-step can be rebuilt from its state directory by aos inspect, with no model. A run that stops on a Go error still writes its report and summary.

What Was Done

  • internal/runlog: an append-only JSONL log. Each seq is assigned and its line written under a file lock (<file>.lock), so seq is gap-free across goroutines and processes. Each line is fsynced before Append returns. The last seq is found by scanning backward, so a torn last line from a killed writer is skipped by readers and newline-terminated by the next writer.
  • Durable trace (<state-dir>/run/trace.jsonl). agentflow.TraceToLog writes every engine trace event. Start, exit, runtime-error, cancelled and capability_denied records carry the matching kernel_event. kernel.RecordEvent now returns the event it logged, so denials can name theirs. agentflow.Tracers fans out to the file and to stdout or the TUI.
  • Call ledger (<state-dir>/run/calls.jsonl). The OpenAI-compatible backend records each call with its pid, agent, repair flag, usage (prompt, cached and completion tokens), latency, error, params and the sha256 of the exact request body. runtime.CallInfo carries the pid and agent through the context; repair calls are marked with runtime.AsRepair.
  • Cheap prompts. A call stores only the messages appended since its process's previous successful non-repair call, with base giving how many it carries over. A call that does not extend the previous one (after compaction, for example) stores everything, with base 0. So the system prompt is stored once per process, and inference.RebuildRequestBody reproduces any request whose hash matches.
  • aos inspect <state-dir> [--json] [--tail N] (internal/inspect). It shows the process tree with exit records and origins, the processes with no exit record, each process's latest checkpoint, the latest verification verdict, usage per process and in total, and the trace tail.
  • Go-error path. Engine.Run returns the partial summary (root PID, exit code 1, the error) alongside the error. aos run --workflow then still writes the HTML report, with the error first under Issues, and the summary JSON with error, trace_path and calls_path.
  • Harbor adapter. Token counts come from aos inspect --json (total_usage), with the run summary as a fallback. When the agent timed out, so run() recorded nothing, they come from calls.jsonl in the downloaded state dir.
  • TUI. aos-tui writes the same two files under its state dir.

Bug Found Along the Way

Writing the Go-error test showed that an agent whose every model call failed (backend down, with continue_on_tool_error) never wrote a checkpoint. A backend error moves to the next step before checkpointing. The step-limit exit then returned an empty checkpoint ID, and the engine failed with a bare file does not exist that hid the real cause. Two fixes:

  • The step-limit exit now writes a final checkpoint, so the backend errors are on disk.
  • The engine falls back to the returned session when there is no checkpoint.

Such a run is now an ordinary workflow failure: step limit exceeded, exit code 1, and the report is written.

Where This Differs From the Brief

  • The system prompt is not stored as a separate inference_prompt artifact. It is the first record of each process's chain in calls.jsonl (base 0). That keeps prompts out of the artifact graph and the hash next to the request it covers.
  • In aos-tui, the trace file holds the engine trace of delegated agents. The interactive root agent's own steps appear only in the call ledger, which covers every call, and in the kernel log.
  • Only the OpenAI-compatible backend records calls. Other JSONCompleters simply leave calls.jsonl empty.

Limits

  • Both files are diagnostic, not authoritative. They sit in the state directory, so anyone who can write there can edit them, the same limit noted for artifacts in phase 13.
  • The trace is only as fine as the engine's trace events. A step killed between its model call and its trace record shows in the ledger but not in the trace.
