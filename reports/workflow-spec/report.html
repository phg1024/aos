Workflow Specs at v0.1.7: Ten Probes

An earlier design review, written at an older commit, made ten claims about workflow specs. This page checks each one against v0.1.7 (6745ba4), for Chapter 10 (Workflow Specs as Executable Contracts). The probe code is new. The behaviour it measures is v0.1.7's: the probes ran in an export of that tag, and again at fcbe014 (the driver fixes after it), with the same findings. Each probe checks Validate, and then a run whose backend is scripted and returns actions directly, so no model, prompt or parser is involved. No model was called.

  • A one-letter typo removes the verification gate. A spec with "verifcation" is accepted, the block is dropped, and the workflow exits 0 although its checker failed the work (S6).
  • Nothing stops a delegation cycle without a budget. a → b → a and a → a are accepted and recurse until the probe stops them. A step limit does not bound the depth; a shared token budget does (S1, S2).
  • A worker can be its own verifier. With the writer named as verifier, the workflow passes on the writer's own exit (S9).
  • Unreachable agents, typos in agent fields, and a per-agent model are all accepted without a word. That includes an agent holding run, writable / and unconfined_run (S3, S5, S6, S7).
  • The edges that are checked hold. A verifier that is not an agent, or that cannot be reached, is refused. So is an edge that grants more than the parent holds (S5, S9).

How to run them

go test -tags workflowspec -count=1 -v ./bench/spec/

The probes are in bench/spec/spec_test.go, kept out of go test ./... by their build tag. To measure v0.1.7 itself, export the tag (git archive v0.1.7), copy the probe file into it, and run the command there. probe-output.txt is that run. Paths print with the home directory's user name replaced, and the probes print no address or hostname.

The scripted backend returns an action for each step of each agent process. Delegating takes the spawn_agent tool as well as an allowed_agents edge, so the probe specs give their delegators that tool. Specs are decoded with json.Unmarshal, as aos run --workflow decodes them. The probe does not create writable mounts, which aos run does.

S7: what a per-agent model field would have to reach

  • The spec: a field on AgentSpec, best a profile name (scripts/models.json), not a raw model id. A profile also carries the backend kind, base URL, key variable and sampling.
  • The factory: BackendFactory.BackendFor(agent, spec) builds a backend per profile. StaticBackendFactory today holds one Completer, and cmd/aos builds one backend for the run from --profile or the environment.
  • The run record: run.started records one backend (backendRecord). It would need one entry per profile used, and which agents use each.
  • The call ledger: it already records backend, model and params.api on every call, so a mixed run is readable as it is. Each driver needs its own call log, or a shared one.
  • Replay: today it builds one backend from the ledger's first call (internal/replay/replay.go), and it refuses runs with more than one agent process. It would need a backend per agent, built from that agent's first call.
  • Budgets and cost: the token budget counts tokens across models as if they were one currency. The comparison analyzer prices calls by params.api, so it already tells the two kinds apart.

Proposal: what a strict spec contract would refuse at load time

Proposed only; nothing here is implemented. It is ranked by risk: what a mistake costs, and how silently it happens. Every refusal would name the field by its path (agents[1].max_step). Unknown fields would also get the nearest known name. Checked-in workflows would need to pass, or be fixed in the same change, and S10 says they already decode strictly.

  1. Unknown fields, anywhere in the spec. Decode with DisallowUnknownFields, at the top level, in agents, capabilities, mounts, verification and evidence. This is the one gap where a typo silently turns a failing workflow into a passing one ("verifcation"). It also catches dropped limits ("max_step"), dropped authority ("capabilites") and dropped edges ("allowed_agent"). Per-agent model, profile and backend would be refused rather than ignored until they are implemented (D5).
  2. A verifier that can change the work. Refuse a verifier that is work-changing (write_file, edit_file, run, or write paths) or is the agent whose work it judges. Today such a verifier passes its own work (S9), and staleness cannot catch it.
  3. Delegation cycles, self-delegation included. Refuse a cycle in the allowed_agents graph, or accept it only with an explicit depth limit in the spec and a run budget. Without a budget nothing ends the recursion (S1, S2), and step limits do not bound depth.
  4. Evidence nobody can publish. Refuse an evidence publisher that cannot be reached from the entry agent, as an unreachable verifier is refused already. Today the run burns the verifier's steps and ends unverified (S9).
  5. Unreachable agents. Refuse an agent that no edge reaches from the entry agent. Such an agent is dead configuration (S3). When it carries authority, it is authority that one edit makes live, without any review of that grant (S5).
  6. Edges without the tool, and the tool without edges. Refuse allowed_agents without spawn_agent: every delegation along it is refused at run time (S3). Refuse spawn_agent with no allowed_agents, which can delegate to nobody.
  7. Out-of-range limits. Refuse a negative max_steps, and a value above a stated ceiling such as 1,000 (S4). Zero would mean "the default" only when the field is absent. That takes a *int, or refusing an explicit 0.
  8. Host paths that cannot work here. Refuse read-only mounts, read paths and skill roots that do not exist, and writable mounts whose parent does not exist. aos run skips creating those silently (S10). This one is less a contract than a property of the machine it runs on, so it might be a separate preflight that aos run runs and Validate does not.
  9. internal/workflow's engine (S8), off agentflow's path. Refuse an empty plan under required, and the same object as worker and verifier. Return an error when required ends unapproved. Or mark the package demo-only and move the policy vocabulary out of it, so agentflow does not import a harness it does not run.

Already refused, and worth keeping in the chapter as the model of a checked edge: a verifier that is not an agent, or not reachable; a verifier that is the entry agent; an edge that grants more tools, paths, mounts or delegable authority than the parent holds; evidence types under the reserved prefix; and evidence from a publisher without publish_artifact, or without read_file for from_file.

After the spec contract

Items 1 to 7 and 9 of the proposal are now in place. Item 8 is a preflight that aos run runs before anything is spawned, not a rule of Validate. probe-output-after-contract.txt is the S1–S10 run at the contract commit, plus two new rows, S6c and S10c. Those rows read specs through the strict decoder, which v0.1.7 does not have, so they live in bench/spec/contract_test.go, which is left out of a run there. probe-output.txt is unchanged. Rules changed from the proposal.

  • A verifier that can change the work is defined by write scope, not by its tools alone. The rasterizer verifiers hold write_file and run for their own -verification directory, and refusing those tools outright would have broken nine checked-in workflows. The rule as implemented is stated in the error and in the README.
  • A cycle needs max_delegation_depth in the spec, and also a budget at run time. A depth limit alone bounds nesting, not how many processes each level starts. The budget can be the run's (--token-budget, or --time-budget with --strict-time-budget) or one on the entry agent's capabilities.
  • An explicit "max_steps": 0 is refused at decode rather than in Validate, since only the decoder can tell 0 from absent.
  • internal/workflow was fixed rather than marked demo-only. The three fixes were small, and its two callers (aos-demo, aos-demo-live) already treat an error as a failed run. agentflow still imports only its policy vocabulary.
