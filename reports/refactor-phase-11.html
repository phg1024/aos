Phase 11 Report: Recorded Outcomes

Workflow success now rests on kernel exit records rather than on what a model writes. These are the first two runtime-contract items from the aos-book design review: the workflow root follows the entry agent's recorded exit (34f7b5d), and a workflow can require a passing verdict from a designated verifier, which only that verifier's exit can produce.

What Was Done

  • Root follows the entry agent. Engine.Run no longer exits the root with code 0 unconditionally. The entry agent's exit code decides the root's, and RunSummary.ExitStatus records it. aos run --workflow exits non-zero when the root does.
  • Children report their exit. DelegateResult.ExitStatus carries a delegated agent's recorded exit to its parent. It appears as exit_code, exit_reason and exit_retryable fields in the parent's history and in the delegate_result artifact.
  • Verification block. WorkflowSpec.Verification is {policy, verifier}, using workflow.VerificationPolicy. Under required or best_effort, validation checks three things: the verifier exists, it is not the entry agent, and the entry agent can reach it through allowed_agents.
  • Verdict from the kernel. The engine finds the verifier's latest exit among the root's descendant processes, ordered by kernel event sequence, and reads it with Kernel.Await. The verdict is stale if a work-changing delegated agent exited after it. Work-changing means it has write_file, edit_file, run, or write paths.
  • The gate. Under required, a root that would otherwise succeed fails with the reason verification required: no verifier run, …verifier <pid> failed: <reason>, or …verdict stale; <agent> (<pid>) ran after verifier <pid>. best_effort records the verdict without gating.
  • Recorded by the root. The verdict becomes a verification artifact whose producer is the workflow root. It is also in RunSummary.Verification and the summary JSON.
  • Workflows. The four rasterizer workflows and live-reviewed-merge declare required. Their verifiers exit 1 on FAIL, and their PASS/FAIL report files remain as evidence.
  • TUI. The progress row shows verify: pending, pass (pid), FAIL (pid) or stale (agent ran after pid). A failed delegated agent shows as └ agent failed.

Decisions Made

ChoiceWhy
The entry agent is excluded from the freshness check.Its run spans the whole workflow, so it always exits last. The rasterizer coordinators hold write_file for their ledger and final summary, so counting the entry agent would make every verdict stale. Tracking the entry agent's own writes after the verdict belongs to the later capability items.
Runs are ordered by kernel event sequence.Event IDs come from one counter allocated under a lock, so ordering is total and has no clock ties.
best_effort is validated like required.A recorded verdict naming a missing or unreachable verifier is a spec error either way.
Gated exit codes.A failed verdict carries the verifier's code and retryable flag. A stale verdict is code 1 and retryable, because another verifier run may pass. A missing verifier run is code 1 and not retryable. If the entry agent itself failed, its failure takes precedence over any verdict.

Known Gaps

  • The verifier is not independent of the writer: same model, shared writable directories, an unconfined run. These are later design-review items.
  • Agents can still publish an artifact of type verification. Reserving types is a later item. The engine's artifact is the one whose producer is the root.
  • Interactive TUI sessions show the verdict but are not gated.
