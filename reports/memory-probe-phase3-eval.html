Memory Phase 3 Evaluation: Probes

An independent measurement of phase 3 (working memory, evidence, handoff) at commit 74510b7, by the evaluation session. The probe set and plan were frozen in 4b2514c before any sample ran: 10 probes, 9 samples each, under three conditions, for 270 samples in all. Every score below is the frozen regex score unless it is labelled hand-read. Where hand-reading disagrees, both are shown.

Result: with a correct working memory injected, the agent answered from it in one step and got 9/9 on every probe except one (tridata 8/9 frozen, 9/9 hand-read). Without working memory:

  • leaf2-readopted fell to 0/9 (p = 0.00004);
  • the working-memory-only probe fell to 1/9 (p = 0.0004);
  • on the two archive-versus-memory conflict probes, every answer still said "no", but 0/18 gave the measurement that settles it, against 36/36 with memory. 6 of 9 in the harder probe stated a wrong fact.
Dropping the "check working memory" rule hurt one probe: leaf2-readopted fell from 9/9 to 4/9 (p = 0.029).

The cost, measured: a lossy entry gets filled in wrongly. The threadgroup entry says "TG4 kept" without saying what TG4 is. With working memory, 6 of 18 answers called it "4 threads", "four pixels" or "4 samples" (it is a 4x4 tile of 16 threads). Only 2 of the 18 read the archive for it, and both got it right. All 9 answers that had to read the archive described it correctly.

    • no-memory,check-rule: no working memory.
  • When: 2026-10-29T19:06:50Z to 2026-10-30T00:00:24Z (run.log), one request at a time. All 270 samples finished, with no errors.
  • Overlap: phg-gpu was shared the whole time with the phase-3 live run (reports/pathtracer-bunny-phase3). Until 20:34:00Z it was also shared with aos code's probe loop. aos book approved the overlap after a check: the live client's timeout is 3600 s, the worst latency seen was 278 s, there are no retries, and the workflow has no wall-clock budget. Overlap can slow responses, but it does not change their content.
  • What "no memory" exposed. All three conditions ran on the 74510b7 binary, before this session's harness change e528cde (which makes --no-working-memory also strip a checkpoint's own working memory). That change cannot affect this run:
    • The memfix run was made by the pre-phase-1 binary eceb917. Its state has no working_memory artifacts, no memory.* events, and no update_memory calls or handoff notices in any history.
    • The four probed checkpoints (art-001084, art-001094, art-001222, art-001942) have no working_memory or memory_snapshot field.
    • Under --no-working-memory, nothing was injected. No sample's checkpoint carried a working-memory version, and no no-memory sample called update_memory.
    So the no-memory condition had no working memory at all: no header, no search hits in it, no handoff. What it did keep is the phase-3 system prompt, which still describes working memory and the check rule. The 0/9 and 1/9 figures are clean ablations, not lower bounds.
  • Where the working memory comes from: every probe's working memory was written by a probe author: five entries by aos code, and the new entries by this session. These probes measure whether the agent uses a working memory it has. Whether it writes a good one is for the live run and the own-memory evaluation.

Both probes quote the writer log's false note that leaf2 "helped the old 32-byte narrow tree". The settling facts are:

  • the round-2 narrow-tree sweep: leaf 1 at 55.4 ms against leaf 2 at 56.6;

Did the Entry Hold the Detail the Answer Stated?

aos book asked this for every answer that came from working memory. Two checks:

  • Numbers (wmcheck.py).
    • The check takes every decimal number in an answer and looks for it in what that sample was shown: the probe's working memory, the checkpoint's live history, the owner's goal in the prompt header, and the sample's own search and read results. It allows rounding, and means, sums and differences of numbers the answer also states.
    • With memory, 7 of 90 answers state a number found in none of those, and 6 without the check rule. Read by hand, all of them are derived: means of the four W4 runs the live history lists, the verifier limit 1.1 x 0.476 = 0.52, and size estimates such as "~3.7 MB of TriData".
    • No working-memory-sourced answer reported a measurement that does not exist.
  • Details that are not numbers: see the next section.

A Lossy Entry, Filled In Wrongly: TG4's Tile Shape

This is the phase-3 risk named before the run ("TG4 kept…"), now measured. When working memory was present and the entry left a detail out, the agent filled it in wrongly in 6 of 18 answers. Every answer that had to read the archive got it right, 9 of 9.

  • The entry. It reads "TG4 kept: interleaved TG4 45.3 vs TG2 47.0 ms; the blocked sweep that favored TG2 was slot-order bias". It never says what TG4 is.
  • The record. PT_TG is the tile's edge length, so TG4 is a 4x4 tile of 16 threads. This is not in the live messages at art-001084, the goal, the workflow or the archive index the prompt shows. It is in the archive: the renderer comment "Trace threadgroup edge length… 4x4=16 threads", and the round-2 notes ("TG 4x4").

Ablations and Cost

  • Check rule. Dropping the rule mattered on one probe: leaf2-readopted fell from 9/9 to 4/9, with 5 superseded (p = 0.029). There the live history shows the agent re-adopting leaf2 after a fresh 24% A/B. Without the rule, 5 answers trust the fresh measurement over the rejected entry, against 9 without memory at all. On every other probe, results without the rule match those with it.
  • Working memory. Removing it hurt, at the frozen scores:
    • leaf2-readopted (0/9);
    • wm-only-next (1/9; 0/9 hand-read);
    • the conflict probes' reasons (see above).
    decide-leaf2-wide's apparent drop is the pattern error. Probes whose answer is in the live history (leaf2-status, w4-first-ab) do not change.
  • tg-sweep cost against phase 2 (mean steps / mean KB read):
    • phase 2: 4.3 / 19.0
    • memory: 2.0 [1–4] / 4.3
    • no check rule: 2.7 / 11.8
    • no memory: 4.7 / 19.4
    Without working memory, phase 3 costs what phase 2 did.
  • Other probes, memory against no memory:
    • tridata: 1.0 / 0 against 5.4 / 44.2;
    • narrow-tree-wm: 1.4 / 0.3 against 6.8 / 14.8;
    • narrow-tree-own: 1.0 / 0 against 3.6 / 11.8.

Caveats

  • The probe's ID was visible to the agent.
    • memprobe put "memprobe": <probe id> in the probe process's metadata. At 74510b7 the prompt header shows process metadata, so every sample in every condition saw its probe's ID.
    • Earlier phases: the phase-1 and phase-2 work directories show the same metadata on their probe processes. Whether those binaries' headers showed it is not verified here (git was unavailable). No phase-1 or phase-2 answer mentions it. aos code's phase-3 samples mention it twice.
    • Answers that quote it (2 of 270, both tridata-order): memory #8 ("round 3, memprobe "tridata-order"") and no memory #4 ("the metadata note for this round ("memprobe: tridata-order")").
      • Three more name a working-memory entry after the ID. The injected key is "tridata tree order". These are memory #5 and no-check-rule #6, and no-memory #6, which cites "the 'tridata-order' item marked rejected in my working memory" when it had no working memory.
    • Does any ID give away its answer? None contains the fact asked for.
      • tridata-order, tg-sweep, leaf2-status, leaf2-speedup, w4-first-ab and decide-leaf2-wide name only the topic, which the question already names.
      • leaf2-readopted names the re-adoption the probe asks about. The live history at its checkpoint already shows that re-adoption. The name does not say whether it was right, and if anything it leans toward the superseded answer.
      • wm-only-next and narrow-tree-wm name the source ("wm"), not the content: neither says QNODE16 or what the measurements were. With memory the entry is already in the header. Without memory the hint points at nothing. Apart from the two tridata answers above, no no-memory answer claims a working-memory source.
      • narrow-tree-own names nothing beyond the question.
    • So the leak changed the wording of a few tridata answers and planted one false source citation. It cannot have supplied a correct answer, and every condition saw the same IDs.
    • Fixed in internal/memprobe: the metadata now says only "true", and TestProbeIDIsNotShown fails without the fix. This applies to later evaluations, not these samples.
  • Small samples. n = 9: a 9/9 against 7/9 difference is p = 0.47. Phase 2 has 3 samples for tg-sweep and w4-first-ab.
  • Only some answers were hand-read. The narrow-tree answers, the misses, the TG4 descriptions and every flagged number were read. Frozen-correct answers on other probes were not re-read for reasons, which is what aos book's reason subsample covers.
  • The working memory is correct by construction. These results show what a correct memory buys and what a terse one costs. They say nothing about memories the agent writes.
