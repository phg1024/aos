Memory Evaluation: The Agent's Own Working Memory

The phase-3 probes injected a hand-written, correct working memory, so they only showed that the agent reads a good memory. This evaluation probes the working memory the agents wrote themselves during the live run reports/pathtracer-bunny-phase3. It follows the plan frozen before any sample ran (reports/memory-probe-own-memory/PLAN.md, commits 34fa829, dd56082). Arm A resumes a checkpoint with its own working memory; arm B resumes the same checkpoint without it. There are 11 probes, 9 samples each per arm, so 198 answers. All ran, with 0 harness errors. Every answer was read by hand.

Result, facts the agent recorded (6 probes): with its own memory the agent answered from the entry in one step every time (54/54) and gave the core fact 54/54, against 43/54 without it, after 4.2 steps on average. With the key detail and no contradicted claim: 43/54 against 34/54. Per probe, A was better on 4, equal on 2, and worse on none. The cost of a recorded fact without memory is search: 0 bytes read against 11,580 on average.

Result, entries the archive contradicts (2 probes): no answer in either arm restated a wrong entry as current (0/18 and 0/18).

  • One stale entry, a shadow bug still marked open, was overridden by live history: A said it was fixed and named the bug 9/9; B only 4/9 (p = 0.029). Five B answers said there had never been a bug.
  • The other, "the Fresnel TIR guard never fires", was not repeated, but it was not corrected either. Both arms answered from textbook physics. Only 1 of 18 answers (in A, after reading the archived code) gave the branch's actual behaviour.

Result, facts the agent did not record (3 probes): own memory neither helped nor hurt. Neither arm recovered any unrecorded fact from the archive when the live context lacked it: 0/18 on the verification directory and 0/18 on the occupancy figure. All 36 of those answers state something the archive contradicts. For example, every answer says no occupancy figure was obtained in round 5, but the agent printed it (1024) at message #33.

Result, a new cost: where an entry compressed a finding, the agent filled the gap with an invented mechanism. All 9 A answers on the round-5 empty-base probe gave the cause the entry held (a cp -R nesting bug), and then explained it with a wrong mechanism the entry did not hold. B searched, and 5/9 found the real one (B better on the exact detail, p = 0.029).

Frozen scores: the frozen regex score and the hand-read exact score differ on 44 of the 198 answers (A 21, B 23). Both are shown below. The frozen patterns were too loose on two probes and matched the wrong clause on two others (details).

Entries the Archive Contradicts

r2-shadow-limit: an open-bug entry that was never closed

  • What the entry said: open/round2-open-bugs in art-000643 says pt_shadow_hit "never compares triangle t against t_limit … must add t < t_limit".
  • What the archive shows: the fix was made at #112. The live history holds the fixed shader, read at #279.
  • Arm A: all 9 said the bug was fixed, named it, and cited the live read at #279. Several quoted the entry as where they had flagged it. None said it was still open.
  • Arm B: all 9 said nothing is open. Four found the bug and its fix by search (#94/#99, #112). The other five said no such bug ever existed.
  • Reading: the stale entry did no harm here, because the live code showed the fix. The entry was the only thing that let the agent say what the bug had been without a search.

r5-tir-guard: an entry that recorded an invented rationale

  • What the entry said: decisions/round5-glass-and-stack says "with ior 1.5 the Fresnel TIR guard never fires".
  • What the code does: pt_fresnel uses eta = ior_t / ior_i (pt_integrator.metal:26; read at #14). The call site passes ior_i = 1 and ior_t = 1.5 for a ray entering the glass (pt_integrator.metal:144–147). So the branch returns 1 for entering rays beyond about 41.8°. For exiting rays it never fires; pt_refract handles real TIR there.
  • Arm A: no answer restated "never fires".
    • 8 of 9 said "yes, for rays inside the glass, never on entry". That is textbook physics and the opposite of this code. Several explained their own entry away: "the shortcut I added was dead, not the TIR branch".
    • 1 of 9 (sample 2) read archived #14 back. It gave the code's real behaviour and corrected its own entry.
  • Arm B: all 9 gave the textbook answer.
  • Frozen score: it marked all 18 as "superseded", because the reject pattern matched "can never fire" in the clause about entering rays. Hand-read, none repeated the entry. This was the live report's C-category instance for pid-000015, and it reached the probe unchanged.

Facts the Agent Did Not Record

  • r2-verify-dir. The verification directory was not readable: #37 "Operation not permitted", #38 "Verification dir not readable (sandbox)".
    • No answer in either arm said so, and no answer tried to list the directory.
    • 4 A and 5 B answers said it was readable, or that they had read it earlier. The rest said they "did not need to open it".
    • The one frozen "correct" (A sample 6) matched the word "sandbox" in "readable from my sandbox".
  • r5-register-counts. At #33 the round-5 writer printed max_threads_per_group trace=1024 with the existing PT_DEBUG=1 hook, and at #35 noted "No offline metal compiler (confirmed). Occupancy proxy max=1024." That message was archived in art-001661 (#30–#120).
    • Late in the live segment (#246–#258) the same writer added a new diagnostic to measure the same figure. It failed to build, and it was not fixed by the checkpoint.
    • All 18 answers describe that failed attempt and say no occupancy figure was obtained this round.
    • The frozen pattern accepted any "couldn't / unable", so it scored 6 A and 8 B correct.
    • No answer searched the archive.
  • r8-sibling-pairs. All 18 answers knew the idea had been rejected, because the round-8 brief lists "32-byte node pairs" as already rejected. The result itself (a wash, n=41, +0.104 ms, writer log line 163) was given by 5 A answers and 2 B answers, all of which grepped the log.
    • This probe was not a clean "unrecorded" control: the brief carried the conclusion into live history.

Reading: the own-memory arm did not hide anything that the no-memory arm found, and the no-memory arm did not search its way to the archived facts either. When the live context lacked a fact and the working memory lacked it too, the agent answered from what it could see and stated the gap as fact.

Did the Cited Entries Hold the Detail?

  • The numbers came from the entries. All 54 A answers to recorded probes answered from the snapshot without a memory call. The figures they gave were in the entries: 4416.3 / 7107 nodes; 107.0 / 126.0 and the revert; 44.493 / 44.425 / 46.042 / 45.607 and 6/8; 30.30 / 0.42; 0/16 and +0.90%.
  • Where the entry was thin, A filled it in. decisions/round5-refs holds "cp -R nesting bug produced nested include/include and a silent shader-compile failure of the base". It does not say why the compile failed.
    • All 9 A answers supplied a reason: the shaders were not found, often "shaders/shaders" as well as include/include.
    • The archive (#73–#76) shows the shaders were present. The base had used the round-3 header (a 36-byte PtTri), so the round-4 shaders failed on pt_v3_16.
    • B, which had to search, found that in 5 of 9 samples.
  • Slips computing from an entry. 2 A answers on r5-entered-stack derived "−0.4 ms on the minimum" from an entry whose minima differ by 0.068 ms.
  • Without memory, B invented history. Its no-memory answers that did not find the archive filled the gap the same way:
    • "hundreds of ms";
    • invented node counts;
    • "the clamp is still in the code";
    • "no shadow bug was ever found";
    • "halving the node was a real win".
    In recorded probes that is 14 contradicted claims, against A's 11. Nine of A's 11 are the one empty-base entry.

Where Frozen and Hand-Read Scores Disagree

The frozen score is compared with the hand-read exact score. They differ on 44 answers. By probe:

  • r5-register-counts (A 6, B 8): the expect pattern accepted any "couldn't / unable / no offline". So answers that denied the archived 1024 figure scored correct. The pattern was too loose; this is a design error by this session.
  • r5-empty-base (A 9, B 1): the pattern accepted "nesting / include/include", which the entry held, so it could not see the wrong mechanism. B sample 9 matched "shader compilation failed" while blaming a bare executable.
  • r8-small-node (B 5): "No" answers that do not know about this round's E5 matched "slower / didn't". B sample 4 matched although it says "yes, a real win".
  • r2-root-exit (B 3): sample 3 matched "rejected"; sample 8 matched although it says the clamp was kept; sample 4 has the right numbers but the wrong round.
  • r2-shadow-limit (A 2): A sample 3 says "it is dealt with" (not in the expect list). A sample 9 hit the reject pattern in a clause about the old state.
  • r5-entered-stack (A 2, B 1): right headline numbers, but a wrong minimum delta.
  • r8-sibling-pairs (B 2): "did not win / no speedup" matched, but these answers gave no recorded result.
  • The rest (5): r2-first-sah (B 2: a wrong magnitude, and invented numbers), r2-verify-dir (A 1, the "sandbox" match), r5-tir-guard (A 1, sample 2: right, but scored superseded), and r8-trace-share (B 1, ~0.3 ms).

The plan's comparisons were run on both scores. Conclusions in this report rest on the hand-read scores where the two differ.

A Missed E3 Instance in the Live Run

Hand-reading r5-register-counts turned up an experiment repeat that the live report's E3 tables do not list.

  • The earlier measurement: the round-5 writer pid-000015 measured the occupancy proxy at #33 (1024).
  • The repeat: at #246–#264 it built a new diagnostic to measure the same figure, "for future experiments". It got 1024 again at #264, after the probe checkpoint. The writer log, line 166, records it as "measured instead of guessed".
  • Why it was missed: #33 had been archived (art-001661) and was never searched. No working-memory entry held it.

This is a category-B instance ("experiment repeated") of the kind the live report counts: the answer was archived and never searched. The live report (464f57c) still says B = 2. It is not changed here. It is reported to aos book as a proposed B3 for pid-000015, to be added with a note if accepted.

Caveats

  • Too few probes for a strong test. There are 11 probes on 3 checkpoints from one run, with 9 samples each. Samples on one probe are not independent, so per-kind pooled p-values overstate the evidence. Sign tests over probes cannot reach 0.05 with 6 or fewer probes.
  • One reader. All hand-reading was by this session, with no second reader. Grades and notes per answer are in handread.py so they can be re-checked.
  • Probe quality. Two probes turned out weaker than designed.
    • r8-sibling-pairs was answerable from the round-8 brief.
    • The frozen patterns for r5-register-counts and r5-empty-base were too loose to score the question asked.
    The probes were not changed after freezing.
  • Final state on disk. The run's files are in their final state, so later writer-log sections were readable in both arms. Only the r8-sibling-pairs answers used them.
  • Scope. Only writer checkpoints qualified under the plan's rule, so the coordinator's working memory was not probed.
