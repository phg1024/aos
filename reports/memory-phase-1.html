Memory Phase 1 Report: Compaction Mechanics

Commits 07e88e5, 4317d9b, 59fb62a, and the review fixes below. Phase 1 of memory-system-design.md. The first live run where agents used read_memory (pathtracer-bunny-memfix) showed four problems. Compaction re-fired almost every step. Segments copied other segments. Reads paged blindly by byte offset. And nothing marked which fact was current. In round 3, the writer took an archived "leaf2 is 27% faster" note as current, re-adopted leaf2, and spent about 20 steps rediscovering that leaf2 was biased. This phase fixes the mechanics without changing the prompt, and adds the replay harness that the later phases are measured with.

What Was Done

  • Message numbering.
    • Message.Seq numbers every message from 1. It is assigned before each compaction and in each checkpoint, and it survives compaction, Resume and Recover. Session.NextSeq holds the last number assigned.
    • Segments record from_seq and to_seq.
    • A checkpoint from before numbering continues after its archived messages, so numbers still count from the start of the process's history.
  • Hysteresis.
    • CompactionPolicy.TargetChars defaults to half the trigger. Compaction archives until live history is at or under the target, so the next compaction is at least the gap away.
    • KeepMessages is now an upper bound, and windowed policies set none. Before, the 12 newest messages were kept whatever their size, so the kept tail alone could exceed the trigger. That was the thrash in the run: 11- and 4-message segments, and live history peaking at 186,200 characters against a 157,000 trigger.
  • Clean cuts.
    • A cut falls only at the start of a turn. A tool result stays with its action, and an action record stays with the message that follows it.
    • The latest turn is never archived. When that turn alone is over the target, it is kept, and the compaction is marked oversized.
  • Observability. Each compaction is a memory.compacted kernel event with its segment, sequence range, live messages and characters, and oversized.
  • No nesting.
    • A read_memory result carries ArchiveAs, a one-hop reference such as read_memory result (art-X, bytes a-b of n): not copied into this segment; read_memory artifact_id=art-X offset=a reads it again. The segment stores that reference instead of the text.
    • Reading a segment back returns the reference, never the text it names.
    • A read_memory result from an older checkpoint is reduced to the segment it named.
  • Precondition. CompactionPolicy.Validate(maxOutput) rejects a policy whose hysteresis gap a single tool output can fill. aos run and aos-tui check it at startup.
    • A 65,536-token window passes: 78,643 characters of headroom against 65,536.
    • A 16,384-token window is refused.
    • The default policy, used when the window is unknown, is exempt.
  • One owner of context. The backend's own history trimming, with its summary and omitted-count fields, is removed, and the prompt carries the session's live history verbatim. Windowed runs never filled those fields, because the runtime compacted first, so their prompts are unchanged.
  • Replay harness. aos probe-memory (internal/memprobe) runs probes against a run.
    • It copies the kernel and the artifact index to a work directory. Payloads are write-once, so they are read in place.
    • For each probe it spawns a process with no tools but read_memory, resumed from the chosen checkpoint as if recovered from its owner.
    • It asks the question several times and scores each answer with expect and reject patterns.
    • It reports correct and superseded answers, steps, reads and bytes per probe.

Each new runtime test was checked by breaking the mechanism it covers: no hysteresis, no clean cuts, reads copied, no legacy numbering base, no legacy reference. Every mutation made its tests fail. The probe test fails when the probe keeps the agent's tools. The full suite passes: go test ./....

Baseline Probe

The baseline used aos probe-memory against reports/pathtracer-bunny-memfix with the probes in bench/memory/pathtracer-bunny-memfix-probes.json. All five probes resume the round-3 writer at checkpoint art-001084 (03:58, five segments archived). The model and parameters were the run's own (phg-gpu Strata, temperature 0.6, top-p 0.95, 65,536-token window), with 3 samples per probe and at most 12 steps each. The segments were written by the old binary, so this measures the current retrieval on the history as it was. The samples are in reports/memory-probe-baseline/.

What it shows.

  • Agents do use read_memory when the answer is only in the archive (TriData: one read each, correct), and they do not read when the answer is live (controls: 0 reads).
  • On the one question that matters, why leaf2 was dropped, all three answers had the verdict right (leaf2 is not a real speedup) and the reason wrong. None recovered the bias. They gave confident, plausible substitutes instead: the number "did not reproduce", "one noisy session", "I never re-ran leaf2 against the RMSE references" (it had, and got 0.79), and one answer said outright "That is not bias".
  • Both samples that read memory chose art-001074, the old binary's nested segment, and got its first page, which is a copy of art-000969. The finding they needed sits in art-001056 past byte 65,536. That is the run's failure reproduced: nesting and blind paging lead to a confident wrong answer. Phase 1 stops new nesting, but the existing segments stay as written.

Scoring.

  • The first baseline (v1/) scored a reply about something else as correct because it contained the word "rejected". Probes now carry a topic pattern that an answer must match before it is scored. Rescored, v1 gives TriData 2/3.
  • The first leaf2-speedup pattern accepted the answers above on stray words such as "bary dropped" and "wash". It now requires the actual finding. aos probe-memory --rescore applies the current patterns to recorded answers without model calls, which is how the table above was scored.
  • Regex scoring catches stray matches only when the pattern names the specific finding, so answers should still be read.

This is the number phases 2 and 3 have to move: leaf2-speedup at 0/3, with the controls staying at 0 reads.

Review Fixes

The book session's verification found two gaps in the contracts as first built. Both are fixed.

  • Validate checked the wrong bound. run capped stdout and stderr separately and echoed the command, so one result could reach about 142 KB, against a gap of 78,643 characters at a 64k window.
    • The two streams now share the 64 KB cap. Each keeps half, and a quiet stream leaves its share to the other.
    • The echoed command is capped at 2 KB.
    • The runtime truncates any recorded result over tools.MaxToolResultBytes (68 KB), and Validate uses that bound.
    • A turn whose own action is larger than the gap can still compact on the next step. No configuration bounds an action's size. That compaction archives a whole turn and is reported as oversized.
    • Tests: TestRunResultFitsTheResultBound, and TestHysteresisHoldsForTheLargestTurn, which runs worst-case results with real run commands, plus a large-action case.
  • A crash could store a range twice. The segment is written before the checkpoint that drops its messages. Segments now record from_seq and to_seq, and a replay from the same checkpoint adopts the existing segment and cuts where it did (adopted=true on the event). It adopts only a segment that no later checkpoint followed. A second deliberate resume from one checkpoint is a fork and still cuts its own segment. Test: TestCompactionIsIdempotentAcrossRecover.
  • Both fixes were mutation-checked: separate stream caps, no backstop, and no adoption each make their tests fail.
  • Evidence count. pid-000009 has two failures of different kinds, now counted separately: a superseded fact cited as current (leaf2 re-adopted at 04:07), and an archived result forgotten with the experiment repeated (leaf2b in art-001220, a question art-001056 had answered).

Not Done Here

  • No prompt changes. The header still lists one ref per segment with a mechanical summary, until phase 2's index. There is no precedence line or working memory, until phase 3.
  • References are byte-based (artifact_id, offset) until phase 2 adds range reads by sequence number.
  • The live path-tracer run still runs on eceb917 and is unaffected.
