2. New Findings

  • N1: Recover is not exclusive. Two sequential Recovers gave two successors, and 20 concurrent ones gave 20.
  • N2: Recover accepts any checkpoint the process owns, not only the one its exit names.
  • N3: Leases are advisory names. The file tools and run never check them, and nothing renews them.
  • N4: After SIGKILL, the holder looks running. Its lease stays held and Recover is refused until aos reap. After the reap, Recover works and moves the lease.
  • N5: aos run has no restart path, and supervisor.RunChildren restarts fresh, with no budget charge or intensity limit.
  • N6: A command cut off mid-flight leaves no record that it started.
    • A7 (cancel): the checkpoint ends tool_cancelled, nothing records the file change, and resuming repeats the effect.
    • A8 (SIGKILL): only the file shows that the command ran.
  • N7: A plain cancel parks the process ready (next: Resume); SIGTERM exits it retryably (next: Recover).
  • N8: Reap labels cleanly parked processes as "orphaned".

3. Contract (summary)

  • Who and when: only an exited, retryable process is recovered, and at most once (superseded_by, in one kernel transaction). Recovery uses the checkpoint the exit names, unless a rollback is explicit and recorded. Capabilities never widen.
  • Restart policy: per agent, with max, within and backoff. Retryable exits restart through Recover. Exceeding the intensity limit gives a final exit, and the failure goes to the parent. Restarts are charged to the same account.
  • Leases: exclusive across processes, and freed on a recorded exit (both implemented). Fencing is checked at the point of effect by the file tools, and a failed check is a lease.fenced event (proposed).
  • Repeats: at most the step in flight. For world tools, a tool.started intent is recorded before the effect. An intent with no outcome is shown to the recovered agent and in inspect. File changes are recorded on cancel too.
