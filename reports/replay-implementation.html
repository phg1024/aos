Replay: Record What Comes From Outside, Re-Run the Rest

This builds the expanded scope of replay-design.md (c53cd79), as the user chose:

  1. start and outcome lines in the call ledger;
  2. a run.started kernel event;
  3. recorded exits on SIGTERM and SIGINT, with the Harbor adapter sending SIGTERM;
  4. file changes recorded on run;
  5. aos replay for single-agent runs.

Refusals stay as they are, with no kernel event.

Result: go vet ./..., go test ./... and the Harbor adapter tests (22) are clean.

  • A recorded CLI run replays identically: every request byte for byte, plus the kernel events, the process table and every artifact.
  • Seven replay tests cover the round trip, divergence at the right call, the pinned clock, token and strict budgets, a killed run, and a ledger cut short.

No live trial has been replayed yet. As the user chose, the Terminal-Bench re-recordings go to the eval session.

1. Ledger: a Start and an Outcome per Call

LineWrittenHolds
"phase":"start"Before the request is sent, syncedpid, agent, step, elapsed_s (the run's seconds when the step began), run (the run.started event), params, delta messages (base = the previous start's seq), request_sha256
"phase":"outcome"When the call returnsstart (its start's seq), usage, latency, error, response (the raw reply)
  • Calls in flight: a start that no outcome names was in flight at a kill. inference.InFlight lists such starts, aos inspect shows them as in_flight per process, and the Harbor adapter records in_flight in the trial metadata.
  • Torn lines are skipped, as runlog promises. A test cuts the ledger after a start, with a half line behind it.
  • Ledger readers:
    • aos inspect and the Harbor adapter count only finished calls, and still read old ledgers.
    • Eval's frozen collect.py counts lines, so on new ledgers it would count each call twice.

2. The Clock, Read Once per Step

  • Each step reads the clock once. Its budget notes come from that reading, and its calls record the run's seconds at that reading as elapsed_s.
  • A replay sets each step's reading back to exactly that value, so the notes come out byte for byte, with no rounding at a second boundary.
  • Seams: Clock, StepClock and Sleep on the runtime and the engine, Kernel.SetClock and Store.SetClock.

3. run.started and run_spec

Right after the root process starts, the engine writes:

  • a run_spec artifact holding the workflow as run and the request;
  • a run.started kernel event on the root process.

4. Signals

  • aos run turns the first SIGTERM or SIGINT into a cancellation with runtime.ErrTerminated as its cause. The runtime then ends each process as a strict budget does:
    • the exit is {1, "terminated by signal (SIGTERM)", retryable}, with a final checkpoint;
    • the call in flight gets its outcome line, with the cause as its error;
    • a running command's process group is killed;
    • the summary is written, and nothing is left running.
    A second signal kills outright.
  • Harbor adapter: Harbor's timeout cancels run() through asyncio.wait_for, which waits for the coroutine to finish its cleanup. The adapter catches the cancellation, runs TERMINATE_COMMAND as root, waits up to 15 s, and re-raises, so the ending is on disk before Harbor collects the logs.
    • TERMINATE_COMMAND finds aos by /proc/*/comm, so it never matches its own shell, and uses the shell's own kill, so it does not need procps.
    • Checked in a real task image (alexgshaw/fix-git, amd64 under emulation): one process named aos before, exit 0, none after.

5. File Changes on run

  • tools.FileChanges compares the workspace mount's size and mtime before and after a command, as created, modified and deleted, capped at 200 with a count of the rest.
  • It is stored in the tool_result artifact and shown in the trace as files=+a,~b,-c.
  • The agent's message is unchanged. It is built from the output only, so prompts and replays are unaffected.

The CLI smoke run repeated seq 27's case, a heredoc script writing the answer:

trace: run command=python3 - <<'PY' import json json.dump({'ok': True}, open('result.json','w')) PY cat result.json … files=+result.json
tool_result changes: {"root": ".../ws", "created": ["result.json"]}

Not covered:

  • writes outside the workspace mount, such as apt install under Terminal-Bench's / grant;
  • a write that keeps a file's size and mtime;
  • trees over 50,000 entries, which are recorded as unknown.

6. aos replay

internal/replay loads the record read-only and rebuilds the engine from run.started and run_spec. It then runs the workflow for real.

Input from outsideIn the replay
Model repliesVLLMConfig.Replayer. The real backend builds each request. The replay checks its hash against the recorded start, then answers with the recorded outcome: reply, usage or error.
World toolstools.Runtime.Recorded answers with the recorded outcome at the artifact ID the replayed outcome will get. That position is unambiguous, because the run is identical up to there. Recorded refusals are rebuilt with tools.RecordedError, so they still log capability.denied.
ClockEach step gets the origin plus its recorded elapsed_s, and other budget reads get the origin. The kernel and the store get the recorded timestamps, in order. Retry waits are skipped.
Strict stop or signalThe call or command that was cut off is stopped with the cause rebuilt from the process's recorded exit, so the exit reason matches.
  • Verdict: every request hash, every kernel event (timestamps included), the process table, and every artifact (record, creation time and payload). Two things are left out: the payload path, and a checkpoint's usage seconds, which come from the wall clock at save time.
  • First divergence: reported by kind, call, step and pid, with the differing message clipped around the first differing character.
  • Exit codes: 0 when identical, 1 at a divergence, 2 when the run cannot be replayed (a multi-agent run, an old ledger, or no run.started).

Limits

  • Single-agent workflow runs only. Multi-agent runs need a recorded schedule, and TUI sessions need their user input fed back in.
  • A step with no model call, such as the one where a token budget stops the run, has no recorded reading and keeps the previous step's.
  • An account below the run's that has its own time limit reads the run's origin, so its notes could differ. No single-agent run has one.
  • A replay by another build says so. Divergence is then the expected signal, not an error.

Not Changed

  • Refusals stay as they are, with no kernel event, as decided.
  • The least-privilege probe results. go test ./... rewrites them, and they are left uncommitted.
  • Nothing pushed, and nothing run on phg-gpu: the evidence above uses local fake servers and one task image.
