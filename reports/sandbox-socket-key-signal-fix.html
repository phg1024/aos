Sandbox Socket, Key and Signal Fixes

Before this work a confined command on Linux could leave the sandbox: the user's service manager ran a command for it. That route is now closed, in ab0950b, on top of 2d7c390. Nothing is pushed. No live model or real kernel ran.

  • Measured on the target machine: the same command through the same helper form escaped before and is refused after. All 14 mutations of the controls fail a test. cuInit, nvidia-smi and nvcc still work under the filter, and one Ray dry job succeeded.
  • Not yet measured: a CUDA allocation or kernel under the filter. The first one is in the preflight, in the offload window.
  • macOS, corrected later: this report guessed a similar route through launchctl submit. Measured afterwards, launchd refused it. What was open was narrower: see the launchd report.

2. Fix 1: the socket filter

Installed in the helper after Landlock and before exec, in hand-assembled BPF with no dependency. Refusals return EPERM, so a tool's error can be read. A filter that cannot be installed refuses the run with exit 126, and an architecture with no filter or a kernel with no seccomp is ErrUnavailable, so run is refused.

  • Why socketpair stays: Python and build tools use it for local IPC. A connected pair reaches nothing outside the process tree, and connect on one was refused every time. A datagram pair could be pointed elsewhere by its nature, so it is refused.
  • Why seqpacket under allow_gpu: a user decision, after measuring that cuInit returns 304 without it. CUDA makes one seqpacket socket to look for MPS and one to listen on its own abstract name. Such a socket gets protocol wrong type for socket from a stream listener, which is what the buses are.
  • Inherited sockets: exec.Cmd closes only what is close-on-exec, so a socket aos was started with would have carried through. The helper now marks every descriptor above stderr close-on-exec just before exec. The run tool passes buffers, so stdout and stderr are pipes, and stdin is empty.
  • What a real workload loses: Python's multiprocessing.Manager. Its Pool and Queue failed before this work too, with a different error, which was not investigated. git, gcc, make, cmake, node, getent, and name lookups with network all still work.
  • Ordering: Landlock first, then the filter, then exec. The filter does not touch close_range or execve, and the helper is what the tests above run, in this order.

3. Fix 2: API keys

Policy.Environment, the one place a confined command's environment is built on both platforms, removes AOS_LLM_API_KEY, AOS_VLLM_API_KEY and AOS_KEY_*. The repository has no allow_env-style grant, so nothing can name them back in. /proc/$PPID/environ stays refused, tested with the keys set in the parent. What the search found beyond these:

  • Provider code reads only those two variables by name. Any profile's api_key_env can be another name. Only aos-tui loads profiles, and it removes those from its own environment. aos run does not read profiles.
  • unconfined_run is unchanged. It inherits everything, keys included. That covers workflows/terminal-bench.json, and bench/harbor/aos_agent.py sets a key, so a model's commands in those containers still see it. Not changed here because the request was for confined commands. It needs its own decision.
  • Other credentials in aos's environment pass through. The environment is copied, not allow-listed. AOS_LLM_BASE_URL passes too, which matters only if a URL carries a credential.
  • Which version: ab0950b, after v0.1.5 and untagged. The eval session's runs keep the old behaviour until they rebuild.

4. Fix 3: signals and abstract sockets

The Landlock ruleset sets LANDLOCK_SCOPE_SIGNAL and LANDLOCK_SCOPE_ABSTRACT_UNIX_SOCKET from ABI 6. A confined kill -TERM of an outside process of the same user is refused and the process lives. A command still signals its own child: status 143. CUDA's own abstract listener still works, in the same domain.

Below ABI 6 follows both existing policies, on the line they already draw. What a policy explicitly asks for and cannot be kept is refused, as network is below ABI 4: allow_gpu is refused, because its seqpacket allowance depends on the abstract scope. A hardening the policy did not ask for is best effort, as truncate and ioctl rights are: the command runs. Unlike those, it is told: aos sandbox: warning: Landlock ABI N cannot scope signals (needs 6), so this command can signal this user's other processes goes to stderr, so it reaches the tool result and the run record. Refusing outright would have stopped every confined run on kernels before 6.12. Only the decision logic was tested for this, since no older kernel was available.

7. Remaining gaps

  • A CUDA allocation or kernel under the filter is unmeasured. It may ask for more. If so it comes back as a decision, without widening the filter first.
  • allow_gpu can reach a seqpacket listener at any path the user can write to, such as /tmp/nvidia-mps/control if MPS is started. A test states this directly. None runs on the machine now. It may also write oom_score_adj and coredump_filter of this user's processes, since /proc stays writable, and the signal scope does not cover that.
  • Shared nvidiactl and nvidia-uvm on a host with a second NVIDIA card remain unmeasured.
  • allow_network sends UDP as well as TCP, anywhere. Unchanged, and by grant.
  • The filter on arm64 has never run. Its numbers are checked only by the interpreter. One kernel, x86-64, was measured.
  • Below ABI 6, nothing ran on a real older kernel. Landlock ABI 9's Unix socket right (documentation patch) would allow-list socket paths and is not used, since this machine cannot test it.
  • Same-user reach is now measured, in section 9. ptrace, pidfd_getfd and the others were refused. Still open from that run: /proc/<pid>/fd can be listed, which shows descriptor numbers; pidfd_open succeeds, though each use tried was refused; /proc/keys is readable, 13 lines, and keyctl was not probed; a user, mount and network namespace can be created inside, where socket and mount stay refused.
  • aos run --input ... --output with a procedural goal runs model-generated Python with no sandbox, and it inherits the keys (internal/app/assemble.go:164). It is not on the workflow path. Not fixed: this needs the user's decision.
  • macOS and unconfined_run: sections 3 and 6.

8. What changes for the workflow and the live run

Nothing in workflows/rasterizer-bunny-cuda-ipc.json, job.sh or submit.sh, and the commands are the same. aos on the machine is now ab0950b. A key passed to job.sh still reaches aos and no longer reaches its commands. Its planned file is outside every mount in the workflow. Docs corrected: README.md, the header of sandbox_linux.go, and a note in reports/ipc-live/cuda-report.html. ipc-design.md makes no claim about Landlock and was left alone.
