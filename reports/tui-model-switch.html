/model: Switching Models Mid-Session in aos-tui

The user asked for a /model command to change models during a session, for example from the Strata on phg-gpu to the Strata on this Mac.

/model lists named endpoint profiles and switches between them. The switch takes effect from the next model call, the session carries over, and the switch is recorded.

Result:

  • go vet ./... and go test ./... are clean.
  • A live smoke test switched from phg-gpu to the local Strata in one session. The second model answered with the first model's history, the records show which endpoint answered each call, and a relaunch came back on the chosen model.
  • No key appeared in the state directory or the output.

Usage

  • /model lists the profiles, with the current one marked *. It uses the same ↑/↓ and Enter picker as /resume, or a numbered list where no picker is available.
  • /model NAME or /model N switches.
  • /help lists the command.
  • /state shows the profile, the model and the endpoint.
  • The startup banner shows the profile. A resumed session also says when it went back to the model its last switch chose.

Profiles

A profile (internal/inference/profiles.go) holds:

  • name, description, backend, base_url, model;
  • api_key_env, the name of the variable that holds the key;
  • the driver settings: context_window, compact_ratio, timeout_seconds and sampling (temperature, top_p, max_tokens, thinking_budget).

The thinking budget and the other driver settings travel with the profile, so no model needs special-casing. There is no separate action-format setting in the driver today, so a profile has none to carry.

Where profiles come from.

  • The first profile is the backend the TUI started with, from AOS_LLM_*. It is named by AOS_MODEL_PROFILE, which tui.sh sets to its preset name, or else env.
    • Without a profiles file, it is the only profile, so nothing changes for existing setups.
    • A file profile with the same name is replaced by it, because the environment is what was actually launched.
  • The other profiles come from a file: --models, else AOS_MODELS_FILE, else ~/.config/aos/models.json (honouring XDG_CONFIG_HOME).
    • Profiles belong to the user, not to one session, so they live in a per-user config directory rather than in a state directory.
    • tui.sh uses the user's file when there is one, else the checked-in scripts/models.json. That file holds tui.sh's own presets with their existing settings.
    • The local Strata profile is strata: http://127.0.0.1:8080, qwen3.8-flash-next-unsloth-ud-q4_k_xl, no key, a 262144-token window, as tui.sh strata sets it.
  • The loader refuses a profile that holds an api_key field, a repeated name, a missing base URL or model, an unknown field, or a ratio outside 0 to 1. Its error messages never repeat the key.

Keys

  • A profile names its key's variable, for example AOS_KEY_STRATA_PHG. tui.sh fills AOS_KEY_STRATA_PHG and AOS_KEY_STRATA_PHG_VLLM from ~/.hermes/config.yaml when they are not already set.
  • A profile whose variable is not set is listed but refused, with the variable's name in the message.
  • The TUI drops every key variable from its environment once it has read them, including AOS_LLM_API_KEY. Until now, run commands inherited AOS_LLM_API_KEY, so the agent's commands could read it. More key variables would have widened that leak, so this closes it.
    • /resume restarts the TUI with the environment it was launched with, so the restarted TUI still has its keys.
  • web_fetch refuses every profile's host, not only the current one's.
  • Keys appear in neither the event nor the ledger. The tests check this, and the smoke test grepped the state directory and the output for the phg-gpu key and found nothing.

Semantics

  • When it applies: from the next model call. The prompt backends call a swappable client, so the root agent and, in workflow mode, its delegates all move to the new model. /model runs only between turns.
  • What carries over: the process, history, working memory, archive and budgets. Tokens keep counting against the same budget.
  • Prompt cache: lost. The new server starts cold.
  • Compaction follows the new model's window:
    • The trigger H is window × ratio × 3 characters and the target L is H/2, as at startup.
    • The runtime's and the workflow engine's policies are both replaced, and the new policy must pass the same validation as at startup.
    • A profile with no window falls back to the runtime's default policy.
  • History already over the new H: the switch is accepted with a warning. The next message starts with the usual handoff on the new model, where the agent updates its working memory, and then the history is compacted.
  • History larger than the new window itself (estimated at 3 characters per token): the switch is refused. Not even the handoff call could be sent, and failed calls would only retry for about 10 minutes.
  • Tokenizer: the exact-tokenizer sidecar is restarted for the new model. If that fails, it falls back to the heuristic count.

Records

Event: model.switched, a kernel event on the root process, recorded before the switch. If recording fails, nothing changes. Its data:

FieldMeaning
from, toProfile names
backend, base_url, modelThe new endpoint
api_key_envThe key's variable name (only when the profile names one)
context_window, compact_at_chars, compact_to_charsThe new window and compaction thresholds H and L (only with a known window)
  • Which model answered which call: the call ledger already records each call's backend (base URL) and model, so the record shows it per call with no change. Linking a call to its step is still open; it is gap "step and clock per call" in replay-design.md.
  • Resume and recover:
    • /recover keeps the current model, since it runs in the same TUI.
    • A resumed session (/resume, or starting on its --state-dir) reads the latest model.switched event in the state directory and goes back to that profile.
    • If that profile is no longer in the file, or its key is missing, the session starts on the launch backend and says why.
  • Why an event and not a field in Session: the event is durable and in the state directory, which is the session. It also survives a switch made before any checkpoint, and a new agent that continues an ended one. A field in each checkpoint would be a second copy that could disagree with the event.
