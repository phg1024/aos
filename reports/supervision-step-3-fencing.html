Supervision Step 3: Lease Fencing for File Writes

This is step 3 of the slice in supervision-design.md, built for Chapter 7. It covers gap N3 and the review's gap 4, for write_file and edit_file. run stays unfenced, as the note decided.

  • acquire_lease shows its fencing token.
  • A write under another process's live lease is refused, and so is a write with a stale token. The refusal is ErrLeaseFenced, a lease.fenced kernel event and a tool error.
  • The check, the tool.started intent and the write all run under the lease lock, so there is no window between check and write.

Result:

  • go vet, go test ./... (25 packages) and the audit probes pass.
  • Probe A4's stale holder no longer writes.
  • Eval's three ca78ad9 trials replay identically.

1. The Rule

  • Which leases cover a write. A lease's resource names a path. An absolute resource is used as is; a relative one is joined to the workspace mount (else the first mount). It covers that path and everything below it, within the process's mounts. A name such as build-lock covers only <workspace>/build-lock, and src does not cover srcfile.
  • The checks, for each covering lease in name order:
    • held_by_other: a live lease held by a process that is not the writer, or a process the writer was recovered from.
    • stale_token: the writer held the resource once, and it has since been granted again. To write, the agent must acquire it again. A writer whose own lease lapsed, with no one granted it since, still holds the current token.
  • What the agent sees is a tool error with no times in it, so it reads the same in a replay. For example: write fenced by a lease: your token 1 for "c.go" is stale; it was granted again with token 2 (no one holds it now); acquire_lease again before writing.
  • Renewal. Nothing renews leases automatically, so there is no failed renewal to report. An acquire_lease that loses to another holder already returns held: true and the holder.

2. Order and Window

  • Order: fence, then intent, then write. All three run inside lease.Manager.Guard. A refused write records no tool.started, so it leaves no open intent and needs no outcome.
  • No window between check and write. Every grant, renewal, takeover and transfer takes the same file lock that Guard holds, across OS processes too. TestGuardHoldsTheLockThroughTheWrite starts a takeover during the write, from a second manager; it completes only after the write.
  • What stays open is writes that do not go through Guard:
    • run. Probe A4b: the same stale holder still writes the file with a command, and no lease.fenced is recorded.
    • Anything outside AOS's tools.

4. Replay

  • Two changes reach replay, because acquire_lease and the fence check run live there:
    • acquire_lease is a runtime tool, so its new token output is written during replay;
    • the fence check runs during replay too.
    Recorded tool results do not cover either.
  • The marker. run.started now records lease_fencing: file_writes. A record without it is replayed with NoLeaseFencing: no fence check and no token. The report sets legacy_leases, and the CLI says the record predates lease fencing; replayed without it.
  • lease.fenced only happens with fencing on. An unfenced replay never records it.
  • A run that acquires a lease has never replayed identically, before this change or after. lease.acquired and the acquire_lease result carry an expires_at from the wall clock, so replay diverges at that kernel event. A throwaway probe showed this both with and without fencing. It dates from f3eef1d and is not fixed here.

6. Behavior That Changed for Existing Runs

  • A write_file or edit_file under another live process's lease, or with a stale token, is now a tool error. Without ContinueOnToolError it ends the run, as a denial does.
  • acquire_lease output has token.
  • run.started has lease_fencing.
  • Every write_file and edit_file takes the lease file's lock and reads leases.json, even when no leases exist.
  • leases.json gains holders.
  • Runs that never acquire a lease behave as before, apart from the lock and the run.started field.
