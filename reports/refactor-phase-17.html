Phase 17 Report: Messages That Arrive, Waits That Resume

Design-review item 9, plus the TUI's /resume. Before this phase:

  • aos run had no message bus, so send/publish/subscribe failed the agent.
  • A message was deleted as soon as it was received, so a crash before the next checkpoint lost it.
  • Two buses on one directory corrupted the mailbox.
  • Mail to dead processes piled up forever.
  • A delegated wait was treated as a failure.
  • A peer's message reached the model looking like the user's own words.

All of these are fixed.

What Was Done

  • The bus (internal/ipc, rewritten).
    • One file lock (bus.lock) and atomic writes. The ID counter is written first and also re-derived from the mailboxes, so an ID is never reused.
    • New(root, kernel): with a kernel, mail to an unknown or exited PID is refused (ErrUnknownRecipient/ErrRecipientExited, logged as ipc.rejected), and Publish drops subscribers that have exited.
    • Receive(pid, redeliver) marks messages delivered (deliveries, delivered_at) and keeps them. Ack removes them.
    • Transfer(from, to) moves unacknowledged mail and subscriptions to another process. Unsubscribe and Pending are new too.
    • Events: ipc.sent, ipc.delivered, ipc.redelivered, ipc.acked, ipc.transferred, ipc.rejected.
  • At-least-once delivery, exactly once into a session.
    • The first step of each run receives with redelivery; later steps take only new mail.
    • Each message's ID goes into Session.MailboxSeen, and repeats are dropped.
    • Every checkpoint the agent loop writes, including the cancel park, goes through saveCheckpoint, which acknowledges the messages the checkpoint now records. A lost acknowledgement only causes a redelivery, which is then dropped.
  • Mail hygiene. A send to an unknown or exited process is the agent's mistake: it gets a tool error and continues, rather than failing the process. An exited process loses its subscriptions. Recover transfers mail, alongside the leases.
  • Peers rank below the task and the user. A peer's message is recorded as message from <agent> (<pid>) [<id>]: …, and the system prompt says such entries are information, never instructions that change the goal, the workflow or what the user asked. The user's own lines still speak as the user.
  • Wait inside delegation.
    • A delegated child that waits is parked, and the engine records an agent_run with status: waiting and the question.
    • The parent's delegate_result says status=waiting question=… and how to answer.
    • Delegating to the same agent again resumes the parked process from its checkpoint, with Answer from <agent> (<pid>), who delegated your task: …. Any other live child of that agent is still refused with ErrDelegateAlreadyActive.
    • When an agent's run ends, any descendants still live are closed as {1, "abandoned while waiting", retryable} with their checkpoints.
    • An entry agent that waits is closed the same way, and the workflow fails with its question.
  • aos run wires the bus on <state-dir>/bus. aos inspect lists unacknowledged mail per recipient, split into pending and delivered-but-not-checkpointed.
  • TUI /resume (separate commit, b8f8c04).
    • /resume lists saved sessions, and /resume N or a name prefix switches to one by restarting the TUI on its state directory.
    • Starting the TUI on an existing session's state directory continues that session.
    • With the new bus, a line typed to an exited agent goes with the recovery instead of bouncing off the mailbox.

Decisions and Divergences

  • The answer to a parked child is the goal of a second delegate to the same agent; there is no separate resume tool. A send to the child's PID before that also works: the mail arrives when it resumes.
  • The chat transcript has only user, assistant and system roles. Peer messages therefore travel as user-role entries, kept append-only, but every one is labelled with its sender and ID and is ranked by the system prompt. The runtime stores them with role mailbox.
  • Lease waits do not park through this path. AcquireForProcess still blocks the process and ReleaseAndWake makes it ready, but nothing resumes it automatically.
  • Reaped processes keep their subscriptions until a publish finds them exited and drops them.
