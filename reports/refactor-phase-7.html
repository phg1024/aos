Phase 7 Report

Verification moves from a hardcoded step to a workflow policy, in both the contract harness and the direct assemble path. This follows the "Verification Must Become Optional" section of AOS_REFACTOR_PLAN.md.

What Was Done

  • Added workflow.VerificationPolicy with none, required and best_effort, plus ParseVerificationPolicy, in internal/workflow/contracts.go.
  • workflow.Engine.Verifier is now optional. A new Engine.Verification field picks the policy. Under none, the engine spawns no verifier process and writes no verification artifact.
  • TaskResult now carries verification_policy and accepted. approved still means "a verifier approved it".
  • internal/app/assemble.go sends both synthesis mode and procedural mode through one verifyOutput helper, controlled by AssembleRequest.Verification.
  • aos run gained --verify none|required|best_effort for runs without a workflow spec.
  • The scenario harness and cmd/aos-demo-live now ask for required explicitly, so their behaviour is unchanged.

Policy Semantics

PolicyContract engineAssemble path
noneOne worker attempt, accepted as-is. Configuring a verifier as well is rejected as a misconfiguration.No verifier call. Output is written.
requiredRetries until approved or attempts run out. Accepted only if approved. A verifier error fails the run.A rejection returns ErrVerificationFailed and the output is not kept.
best_effortRetries on rejection, then accepts the last output. A verifier error is recorded and the output is accepted.The verdict and reason are recorded. Output is always kept.

Decisions Made

  • An empty Engine.Verification resolves to required when a verifier is configured, and to none otherwise. Core never adds a verifier the caller did not supply.
  • The aos run assemble path now defaults to none. This is a behaviour change: earlier it always ran a verifier. Pass --verify required to get the old gate back.
  • The manual policy from the refactor plan is not implemented yet, because it needs a human-approval wait state in the runtime.
  • The planner and worker roles of the contract harness stay as they are. The package is documented as one workflow pattern, not as core semantics.
