### A — pid-000003 #173 — writer log describes the Fresnel TIR test the opposite way from the code it wrote
- Claim: shared writer log line 20, written at #173: "Schlick Fresnel (TIR test uses (n_i/n_t)^2, R0 uses ((n_i-n_t)/(n_i+n_t))^2)".
- Already available: its own edit at #116 (art-000183, live): "const float eta = ior_t / ior_i; const float sin2_t = eta * eta * (1.0f - c * c); if (sin2_t > 1.0f) { return 1.0f; // total internal reflection". So the test uses (n_t/n_i)^2. The #116 note shows the intent ("TIR test needs (n_i/n_t)^2"), but the code does the reverse. The next writer confirmed the reversed form at pid-000006 #262: "pt_fresnel's TIR test uses (ior_t/ior_i)^2 while pt_refract uses (ior_i/ior_t)^2".
- Acted on: recorded in the shared writer log (#173), which round 2 reads at pid-000006 #30. The same Fresnel is the frozen reference, so the error matters: rays entering the glass above about 41.8 deg get total reflection.
- Confidence: medium. The log line is plainly wrong against code that was in live context. But the root is a coding slip at #116, where the agent wrote the code against its own stated intent, not a lost memory. If the eval only counts recall failures, drop this one.

- Experiment: #301: "Next: shrink the per-thread traversal stack 20 -> 16 (tree depth is capped at 15, ...) to cut register pressure and raise occupancy." Built and benchmarked at #303/#304 (render_ms_best=76.353, a regression), reverted at #305.

Its stated motivation then was the same as now (#122: "shrink the per-thread traversal stack from 20 to 16 entries to cut register/local pressure").
- Acted on: rebuilt, benchmarked and reverted (#303-#305). The rejection then went into the log as if it were a new finding (log line 68: "shrinking PT_BVH_STACK_SIZE 20->16 (76.4ms, #304)").
- Confidence: high that this repeats an experiment already in WM with no mention of it. The kernel had changed since #122 (near-first traversal, #280-#284), which could make a rerun new. The agent never gave that as a reason, though. Its only reason is a safety argument, and #303 repeats the archived #122 configuration ("caps depth at PT_BVH_MAX_DEPTH=15"). So it recalled the setup of the earlier test but not its result.

### A — pid-000006 #268 — says "MATH_UNCHANGED confirms the normalize removal is bit-identical", but the reference PFM was rendered after the removal
- Claim: #268: "MATH_UNCHANGED confirms the normalize removal is bit-identical." #266 had set it up: "confirm seed-7 PFM still matches the earlier d1.pfm (proves no statistical change from the normalize removals either)".
- Already available (live): the normalize() removals were edited at #248/#250 and built at #252. out/d1.pfm was then re-rendered from that new binary at #254 ("./pathtracer ... --seed 7 --threads 4 --spp 8 --out ../out/d1.ppm --out-pfm ../out/d1.pfm"), overwriting the round-1 d1.pfm from pid-000003 #138, which was listed at #56. So the #266 cmp compared two post-removal builds and could not test the removal. The merged tone map (#226-#247) also came before d1 and was never compared to an earlier PFM. No pre-change round-2 reference exists: the attempt at #55 to save one failed (#56 "metal init error").
- Acted on: recorded as fact in WM [decisions/round2-keywin] (#286): "removal of two analytic-unit normalize() calls in pt_refract/pt_sample_cosine (90.78, bit-identical)". Also in WM [measurements/round2-final] (#328): "All changes bit-identical PFM (cmp vs out/d1.pfm = MATH_UNCHANGED)". The writer log line 61 (#334) says "Changes kept (each verified bit-identical PFM vs out/d1.pfm, so statistics are untouched)" and covers items 3 (tone map) and 4 (normalize). The exit report #338 says "Kept changes, each verified bit-identical PFM so the estimator is untouched". Round 3's writer log (line 75) follows the same "bit-identical, estimator untouched" framing.
- Corroboration (not available to the writer): pid-000008 #16 measured default RMSE 0.848202, against the frozen round-1 value 0.847970. So the round-2 PFM is not bit-identical to round 1. That fits the normalize removal changing float rounding.
- Confidence: high. The order #252 -> #254 -> #266 is in live context, and the false conclusion was recorded in WM, the shared log and the exit report.

### C — pid-000006 #328/#334/#338 — "register pathology" recorded as the cause of the 478 ms shadow-walk regression; the agent's own code shows a duplicated-traversal bug
- Claim: #292 states it as a hypothesis: "likely register pressure/spill from the extra branch structure in the second inlined traversal". It was then recorded as fact. WM [measurements/round2-final] (#328): "EXPLODED to 478ms (#291, reverted - register pathology)". Writer log line 68 (#334): "EXPLODED to 478ms - register pathology in the second inlined traversal, #291". Exit #338: "(478ms register pathology)".
- Already available / contradicting: no register, occupancy or spill measurement appears anywhere in the history. The #288 edit itself shows a logic fault: "if (hit_right && stack_size < PT_BVH_STACK_SIZE) { stack[stack_size++] = right; } if (hit_left) { node_index = left; continue; } if (hit_right) { node_index = right; continue; }". When only the right child is hit, it is both pushed and descended into, so that subtree is walked twice, and this compounds level by level. An any-hit walk gives the same boolean either way, which matches "MATH_UNCHANGED" at #291. The double walk explains a 7x slowdown with no register effect needed.
- Acted on: recorded in WM, the shared writer log and the exit report. It also spread: round-3 writer log line 81 says "keeps this clear of the register blow-up round 2 saw".
- Confidence: high that the cause is unsupported by any measurement and was recorded as fact. Medium-high that the double walk is the real cause; that is my reading of the #288 code, not measured.
