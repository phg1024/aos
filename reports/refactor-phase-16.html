Phase 16 Report: Confined Run, Network as a Capability

Design-review item 8. Before this phase, run was sh -c as the host user. Mounts and scopes limited only the file tools, so a worker's run could read secrets, write outside its mounts, rewrite the state directory, and (in the Metal workflow) write a PASS verdict into the read-only cpu-reference mount. allow_network was enforced nowhere. Now run executes inside an OS sandbox built from the process's capabilities, or is refused. The web tools need network, and web_fetch cannot reach internal addresses.

What Was Done

  • internal/sandbox (new).
    • macOS: /usr/bin/sandbox-exec with a profile generated per call. The profile denies everything by default. It allows the process's read roots, write roots and per-process scratch directory, plus system and toolchain reads. Read-only roots are denied writes, and the state directory is denied all access; these rules come last, so they override the grants. Only a short list of system services is reachable: directory and logging services, the Metal compiler and the GPU memory service. Name resolution and URL services are left out unless network is allowed.
    • Linux: Landlock through raw syscalls (stdlib only). The binary re-executes itself as a helper, which restricts its own thread and then execs sh. TCP is denied unless network is allowed; this needs Landlock ABI 4, and on older kernels a policy without network is refused. A policy Landlock cannot express, such as a state dir inside a writable root, is refused rather than weakened.
    • Other platforms: unavailable.
  • Fail closed. If run cannot be confined, it fails with ErrRunUnconfined and is logged as capability.denied (unconfined_run). The only exception is a process whose set includes unconfined_run. That field attenuates (Union / DeriveChildSet / Excess), and it appears in the process record, in inspect ([UNCONFINED run]) and in the HTML report. Every run result says how it was confined (confinement).
  • The state directory is protected. tools.Runtime.Protected (the state dir and its lock, set by aos run and aos-tui) is unreachable from run and from the file tools, even where a mount covers it, as with the rasterizer runs' .aos-state.
  • Network as a capability.
    • web_search and web_fetch require allow_network.
    • web_fetch refuses the model endpoint's host, and any address that is loopback, private, link-local, CGNAT (100.64/10), multicast or unspecified. A network_allow entry (host, address or CIDR) overrides this. The check runs at every dial, including redirects, against the address actually dialled, so DNS rebinding cannot slip past it. Proxies are not used.
    • The body is read through a 4 MiB limit.
    • Refusals are logged as capability.denied (network).
  • Bounded timeout. max_run_seconds (default 600) clamps run's timeout and attenuates to the minimum. The result records timeout, timeout_bound and timeout_clamped.
  • Workflow specs.
    • In the four gated rasterizer workflows, the verifier mounts the workspace read-only and gets a new writable <workspace>-verification directory. Its verification report and log move there, and its prompt says to build and render there.
    • The coordinator mounts that directory and may delegate writes to it.
    • aos run creates the directory when its parent exists.
    • The Metal coordinator and writer get allow_network, because they list web_search/web_fetch, which now need it.
    • terminal-bench.json's solver opts in to unconfined_run (it runs inside a disposable container), with max_run_seconds: 900.
  • TUI. In direct mode, the interactive agent gets network when its tool list includes a web tool. That also gives its run network.

Measured on This Mac

  • Real Metal workload under the generated profile (writer layout: writable workspace, read-only cpu-reference). The clang++ … -framework Metal build was clean. With miniforge python3 readable as a toolchain prefix, renders produced byte-identical images. Best render: 0.188–0.226 ms sandboxed vs 0.194–0.231 ms plain, over three runs of 50 frames each, so no overhead. Writing "Overall correctness verdict: PASS" into cpu-reference was refused with "Operation not permitted".
  • Per-call overhead: a warm C++ build and run took 73–76 ms confined vs 65–66 ms unconfined, about 10 ms for compiling the profile.
  • Linux: the Landlock test binary (linux/arm64) ran in an Alpine container on Docker Desktop's 7.0.14 kernel and passed: in-scope writes work, reading a secret, writing outside and writing into the read-only reference fail, TCP is blocked without network and allowed with it, and a state dir nested in a writable root is refused.

What Existing Workflows Need

  • Rasterizer workflows on this Mac: no change for the writer and benchmarker beyond confinement. The verifier now works in <workspace>-verification. Tools from PATH prefixes outside the home directory, plus miniforge-style prefixes inside it, stay readable. A toolchain elsewhere goes in AOS_SANDBOX_READ.
  • Metal: the coordinator and writer now declare allow_network for their web tools.
  • Terminal-Bench: unconfined_run and max_run_seconds: 900, already in the spec.
  • Live merge workflows: file tools only, so unaffected.

Not Covered

  • No CPU, memory, process-count or disk quotas. Only wall time is bounded, by the timeout.
  • macOS: stat works on any path, so a command can learn that a path exists but not read it. GPU access (iokit-open) is open. Allowed system services act on the command's behalf. The profile language is deprecated by Apple, although it is present and works on macOS 27.0.1.
  • Linux: Landlock does not cover UDP, so DNS queries still go out even without network. It cannot carve a denied subtree out of a granted one, so such policies are refused. Rosetta-translated binaries fail under confinement.
  • An unconfined process (unconfined_run) can reach anything its user can, including the network.
