The Inference Driver at v0.1.6: Seven Probes

Seven scripted probes, D1 to D7, measure the model client as it stands at v0.1.6 (8d5ff6e), for Chapter 9. They check how it reads a reply, how it retries, what each provider kind sends, whether an agent can name its own model, how much of the prompt cache live6 reused, and how max_tokens is capped. Every probe runs against a fake server or the local records of live6. None calls a real model. Each probe logs what it ran and what it saw. The probes only measure, so a defect shows up as a finding, not as a failed test.

  • Streaming changes the action. When the reasoning holds an action and the content does not, aos-tui runs the reasoning's action, while aos run asks for a repair (D1).
  • Retries do not tell errors apart. A hung server, a 503 and a 404 each get 12 attempts with 607 s of waits (D2).
  • Four of 18 replies are misread. An example quoted after the real action wins over it, and JSON inside a <think> block wins over prose (D3).
  • One kind is real. vllm, ollama, openai-compatible and even anthropic all build the same chat-completions client (D4). A workflow cannot give an agent its own model, and the field is dropped without a word (D5).
  • The prompt is append-only. 195 of 196 later calls in live6 extend the previous one, and the server reported 94.4% of prompt tokens as cached (D6).

How to run them

go test -tags inferencedriver -count=1 -v ./bench/inference/

The probes are in bench/inference/driver_test.go, kept out of go test ./... by their build tag, as bench/ipc is. The full output of the run behind this page is probe-output.txt, next to it, with the test server's address replaced. D6 needs reports/ipc-live/runs/live6, which is gitignored, and is skipped without it.

One rule for this page and for the book: config.go's default base URL, for the vllm and openai-compatible kinds, is a machine's hostname. Do not print it. The probes report only that it is a hostname.

D1. Streaming and not: the same reply, two actions

The fake server sends the same reply both ways: an action in the reasoning field, and some content. Streamed, it arrives as reasoning_content and content deltas, read with OnStreamEvent set as aos-tui sets it. Not streamed, it arrives as one message, which is how aos run reads it. The reasoning is {"action":{"type":"exit","code":0,"reason":"from reasoning"}} each time. The repair call is answered with a message, "from repair".

Contentaos run (not streamed)aos-tui (streamed)
a valid actionmessage "from content", 1 callmessage "from content", 1 call
prose, no bracesmessage "from repair", 2 callsexit 0 "from reasoning", 1 call
one brace shortmessage "from content", 1 callmessage "from content", 1 call
emptymessage "from repair", 2 callsexit 0 "from reasoning", 1 call
a valid action, with prose and braces in the reasoningmessage "from content", 1 callmessage "from content", 1 call

Why. When streaming, vllm.go writes every reasoning delta into the text it returns, ahead of the content, with no separator. Without streaming it reads only message.content, so the reasoning is dropped. The parser then takes the last complete JSON object in the text. Where the content holds a valid action, both modes agree. Where the content holds no braces, the streamed text's only object is the one in the reasoning, and the agent runs it. In the probe that is an exit 0 the model never committed to.

D2. Retries: one in the driver, 12 in the runtime, for any error

EndpointDriver aloneThrough the runtime
hung (client timeout 50 ms)1 request, context deadline exceeded12 requests, 11 waits totalling 10 min 7 s, exit 1, retryable
5031 request, vllm request failed: 50312 requests, the same waits, exit 1, retryable
4041 request, vllm request failed: 40412 requests, the same waits, exit 1, retryable
  • The driver. NewBackendFromConfig never sets MaxRetries, so max(1, 0) gives one attempt per call. The driver's own loop, which would retry timeouts, 5xx and bad bodies, never repeats.
  • The runtime. BackendRetryPolicy defaults to 12 attempts, waiting 1 s and doubling up to 2 min. The waits are 1, 2, 4, 8, 16, 32 and 64 s, then four of 120 s, which add up to 607 s. That matches cuda-report.html's 12 attempts and 607 s, and live1's ten minutes.
  • The test clock. The probe runs a one-agent workflow through agentflow.Engine, with Sleep recording each wait instead of sleeping, so the 607 s cost 3 s of wall time.
  • Wall time on a real hang. Each attempt also lasts up to the HTTP timeout. So a hung server costs 607 s plus 12 times the timeout: about 4.2 hours (15,007 s) at the 1200 s that the live runs used.
  • Errors are not told apart. The runtime retries any error alike. A 404, or a 400 for a prompt over the limit, gets the same 12 attempts as an outage, and the exit is marked retryable.

D3. The tolerance ladder

Each reply goes through PromptBackend.Generate over a scripted transcript completer, which is the path aos run and aos-tui take. The repair call gets the reply's second line where there is one, and the first again where there is not. "Correct" means the action the reply's author meant.

  • Last complete object wins. extractTrailingJSONObject takes the last suffix that is complete JSON. So an example quoted after the action replaces it, and an object short of its outer brace gives up its inner action. live6's call 28 was the lucky second kind.
  • Prose around JSON. When no suffix is complete JSON, repairLooseJSONObject takes everything from the first brace to the last one. That is how JSON inside a <think> block, followed by prose, becomes the action. It is the same text D1's streamed reply produces.
  • The flat and legacy stages. For well-formed input they are never reached, because the generic stage reads those shapes first. The flat stage is reached only when the generic stage refuses a shape. It then returns an action without checking that it is usable, so the in-transcript repair is skipped. The runtime then treats the delegate as malformed, at runtime.go line 1260.

  • Any other name passes through. normalizeBackendKind keeps an unknown name such as anthropic as it is. It is then sent as the same client to /v1/chat/completions.
  • An Anthropic-only server. One that answers only /v1/messages returns 404 Not Found, and through the runtime that gets 12 attempts, as D2 shows.

D5. A model per agent

The probe gives a workflow a top-level model, and gives its agent model, profile and backend. It decodes the workflow with json.Unmarshal, as aos run does, and the decode succeeds. Validate passes, and after a round trip none of the three fields is left. A decoder with DisallowUnknownFields would refuse it with unknown field "model", but aos run does not use one. StaticBackendFactory.BackendFor hands every agent the one completer. So a workflow cannot give an agent its own model, and a workflow that tries is not told.

D6. Prompt-cache reuse in live6

This probe reads live6's local call ledger. It rebuilds each call's full message list from its base chain, and compares it with the same process's previous non-repair call. The cached-token counts are what the model server reported, not something AOS measured.

The cached share of a whole prompt is lower than the reuse figure because each call adds the new turn and the previous reply, which were never cached. AOS's append-only transcript (PromptMessages) does what it was built for: almost every call's prompt starts with the previous call's prompt, byte for byte.

D7. max_tokens and the token budget

complete() in vllm.go lowers max_tokens to CallInfo.MaxTokens. runtime.go sets that to tokens.Left, the budget left in prompt plus completion tokens. It does not subtract the prompt the call is about to send, so a call near the end of the budget can still overrun it by its prompt. With no budget and no configured value, the code sends no max_tokens and the server's default applies (read from the code, not probed).

Premises against the code

  • D1: confirmed. Streaming puts the reasoning in the text the parser reads. Without streaming, only message.content is read.
  • D2: confirmed, 1 attempt by the driver and 12 by the runtime, with 607 s of waits. Not in the premise: the runtime retries a 404 the same way.
  • D3: mostly confirmed. The flat and legacy stages are not stages for well-formed input, because the generic stage reads those shapes first. The flat stage is reached only for a shape the generic stage refuses, and then it returns an unusable action.
  • D4: confirmed for the bodies. The headers differ too: the ollama kind sends no Authorization header.
  • D5: confirmed. A spec cannot name a model per agent, and the field is dropped silently, not refused.
  • D7: confirmed. The cap is the whole budget left, not what is left after the prompt.
