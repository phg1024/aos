Budget Notes Before the Terminal-Bench Rerun

The Terminal-Bench rerun should measure the budget mechanism as it is now. A read-only survey of 76710c0 found four gaps, and this commit closes them:

  1. The solver prompt still describes the removed clock notes.
  2. The agent is never told its step limit.
  3. A comment states the wrong total retry wait.
  4. The Harbor adapter cannot run without an AOS time budget.

Result: go vet ./..., go test ./... and the Harbor adapter tests (run-tb.sh --self-test, 18 tests) are clean. Nothing was run against a model.

1. The Solver Prompt

In workflows/terminal-bench.json, the budget sentence described the old clock notes, which warned at 20%. It now describes what the runtime emits (internal/runtime/budget.go):

BeforeNow
Time is limited and you think slowly. When a clock note follows your step, it shows the time used and left: have a complete answer saved by half the budget, and when it warns that less than 20% is left, stop exploring, make sure the saved answer is complete and valid, and exit. Time and steps are limited, and you think slowly. Notes before your step show your budgets: budget time=1800s used=600s left=1200s gives the time, and with (strict: the run is stopped when it runs out) the run is stopped at zero, mid-command; near the step limit, budget steps=300 used=275 left=25 gives the steps, this one included. Have a complete answer saved by half the time. When a budget warning comes (less than 10% of the time or steps is left), stop exploring, make sure the saved answer is complete and valid, and exit.
  • The rule to commit a complete answer early and then improve it in place (step 2 of "How to work") is unchanged.
  • The prompt does not promise a time note. With time_budget=off there is none, and the sentence still holds.
  • The workflow test now fails if the prompt mentions "clock note" or "20%", or if it stops describing the notes the runtime emits.

2. The Step Limit

The note: budget steps=<limit> used=<U> left=<L> (strict: the run is stopped after the last step).

  • used counts the steps before this one in the turn, and left includes this one.
  • left starts at the limit, and the last step reads left=1.
  • The limit includes any operator extension.

The warning comes once, with the first note: budget warning: <L> of <limit> steps are left, this one included. Commit your best answer now: write or submit what you have, then exit.

  • It is recorded as steps in BudgetWarned, so it is not repeated.
  • It gives the count rather than "less than 10%" because a limit under ten steps is warned at its last step, which can be more than 10%.

Choice: the note appears only near the limit, in the last tenth of the steps and at least on the last step, rather than on every step.

  • Every run has a step limit. When the spec sets none, it is 32. Time and token notes appear only in runs that set those budgets. A note on every step would add one message per step to every run. I tried that first, and it failed 20 existing tests.
  • It changed the runs themselves, not only their prompts. Notes are messages, so they count toward the compaction window, and segments were cut at different points. Memory probes and least-privilege probes would have measured a different system from their earlier runs.
  • The ablation stays clean. The steps information is the same whatever the time-budget mode, so a strict/off comparison varies only the time budget.
  • Prompt caching is unaffected either way. Notes are appended, so the prompt prefix stays the same.
  • Cost: the agent learns its step allowance only in the last tenth. With the solver's 300 steps, that is from step 271. The prompt says that notes appear near the limit.

A TUI turn (NewTurn) already starts a fresh step allowance at StepBase. It now also clears the steps warning, so each turn is warned at its own end and the note counts only that turn's steps. Time and token warnings stay once per process, as their budgets do.

Runs that reach the last tenth of their steps now see the note. For example, a memory-probe answer with MaxSteps 12 sees it on its 12th step. Runs that end earlier see no change.

3. The Retry Comment

The defaults are 12 attempts, waiting 1 s and doubling up to 2 min. The 11 waits are 1 + 2 + 4 + 8 + 16 + 32 + 64 + 4 × 120 = 607 s, about 10 minutes, not 12. Each attempt also takes up to the backend's HTTP timeout: 120 s for aos, 180 s for aos-tui, or AOS_LLM_TIMEOUT_SECONDS, which the Harbor adapter sets to 3600.

Fixed the comment, not the numbers. The policy is meant to outlast an endpoint restart, and 12 minutes was a miscount, not a target. Changing the numbers just before the rerun would also change how runs behave during an outage. The comment now also says that a strict time budget cuts the waiting short. The same miscount in reports/memory-recall.html is corrected and marked as corrected.

4. The Harbor Time-Budget Switch

bench/harbor/aos_agent.py takes a time_budget agent kwarg, which falls back to the AOS_TIME_BUDGET environment variable and then to strict:

ModeFlags passed to aos run
strict (default, as before)--time-budget <Harbor timeout − setup − 20 s> --strict-time-budget
advisory--time-budget … only: the agent sees the notes and the warning but is not stopped
offnone: no time notes, only Harbor's timeout ends the trial (the pilot's condition)
  • Usage: bench/harbor/run-tb.sh … --ak time_budget=off. Harbor passes off through as a string.
  • An unknown value raises in the agent's constructor, so the job fails before any trial runs.
  • Each trial's metadata records time_budget and the exact time_budget_flag used.
  • The 60 s minimum budget is unchanged. Below it, no budget is passed in any mode.
