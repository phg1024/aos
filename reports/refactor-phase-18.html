Phase 18 Report: Budgets

Design-review item 10, the last in the contract list. Before this phase, the time budget was only a note, there was no token budget, and resuming a process reset its step count. Now budgets are hierarchical, persistent and visible. Token budgets are enforced whenever they are set. A time budget is advisory unless strict_time is set, as the user asked: strict enforcement is opt-in.

What Was Done

  • capability.Budget {tokens, seconds, strict_time}, in every capability set as budget.
    • DeriveChildSet takes the tighter limit, and a strict parent makes the child strict.
    • Union takes the larger budget either set names. A delegable set that names none adds nothing, so it does not make the grant unlimited.
    • Excess reports budget tokens N (at most M), so Validate rejects a child that asks for more than its parent may grant. A child naming no budget inherits its parent's.
  • Accounts (runtime/budget.go).
    • Each run of a process opens an account, chained through the context to its delegator's account, with the run's own account at the top (as cgroups nest).
    • Tokens are charged to the account and every ancestor. Time accrues while the owner runs.
    • Limits are checked as the tightest remaining budget over the chain, and the owner of that budget is named in the exit.
  • Tokens. The runtime puts a TokenMeter and a MaxTokens cap in each call's CallInfo.
    • The backend caps max_tokens to what is left and adds the reported prompt+completion tokens to the meter, cached prompt tokens and repairs included.
    • The limit is checked before each call. A budget can be overshot by at most one call's prompt.
    • A spent budget ends the process with {1, "token budget exceeded: U of L tokens used (budget of …)", retryable} and a final checkpoint.
  • Time.
    • Each step adds a note with the time and tokens left, and once per kind, with less than 10% left, a warning to commit the best answer now (the Terminal-Bench lesson).
    • With strict_time, the run's context gets a deadline whose cause is ErrTimeBudgetExceeded, which cancels the in-flight model call or command, killing a command's whole process group. The process then ends with {1, "time budget exceeded: Ns strict budget of …", retryable} and a checkpoint.
    • Cancel notes say reason=time_budget_exceeded rather than interrupted_by_user.
    • The old Clock is removed: --time-budget now sets the run's budget, advisory unless --strict-time-budget is given. --token-budget N is new.
  • Persistence.
    • The session keeps usage {steps, tokens, seconds}, step_base, extended and budget_warned.
    • Steps count from the checkpoint, so Resume and Recover cannot reset the step limit, and warnings are not repeated.
    • RunOptions.Extend {steps, tokens, seconds} is the operator's explicit grant, accumulated in the session.
    • RunOptions.NewTurn starts a fresh step allowance. The TUI sets it for each message you type; nothing else does.
  • Visibility. aos inspect (text and JSON) and the HTML report's new Budget column show each process's budget and usage from its latest checkpoint, and the exit reason names the budget that ended it.
  • Also: a peer message's body lines that imitate a sender label are quoted with > . This was the book session's optional suggestion from its item-9 probe.

Divergences and Limits

  • Strict time is opt-in (strict_time / --strict-time-budget), at the user's request. An unset or non-strict time budget only advises.
  • Usage is saved in checkpoints. A delegate's tokens are added to its parent's account in memory, so a crash after the delegate finished but before the parent's next checkpoint undercounts the parent. The call ledger (run/calls.jsonl) still has every call.
  • Only backends that report usage are metered (the OpenAI-compatible one does); a server that omits usage costs nothing.
  • Extension is an API (RunOptions.Extend). There is no aos recover --extend CLI yet, since aos has no recover command.
  • The warning fires once, at 10% left (the old clock warned at every step from 20% left). Tokens are the unit; there is no price table.
